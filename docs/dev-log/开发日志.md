## 侦察报告 05 的关键结论（DSH 侧 channel 接入面）

**不存在 channel / connector / bridge seam**。微信 channel ≈ 自造三块：入站适配器 + 会话映射表 + 出站订阅转发器。

- **现成可复用**：`Agent.followup/steer/inject`（入站注入）；`ctx.commands.execute(agent, line, [], signal)`（命令分发，四参数签名 + 非 Web adapter 调用范式）；`ctx.agents.create({meta:{cwd}})`；`ctx.on('session/event')`；`ctx.on('agent/assistant-stream')`；`ctx.webServer.register`；`MessageSourceMap` 声明合并；`ctx.messageFeedback`（微信 👍/👎 可落此）
- **需自己造**：微信入站（登录/长轮询/验签 + 会话映射表）；微信出站（分段/限流/重试）；同会话串行与去重；主动推送触发器
- **明确不存在**：出站投递 seam / 投递目标抽象；**运行时切换 cwd**（`SessionHeader.cwd` immutable）；`webhookRuntime` 的 completion result

**对 Q8 的硬约束**：用户选「默认一个目录 + 工作目录用户可选」——但 **cwd 终生不可变，换目录必须新建 Session**。设计上应表达为「切换工作区 = 切换/新建会话」。

**必做项**：`declare module '@deepseek-ai/dsh-llm' { interface MessageSourceMap { wechat: {...} } }`，否则微信消息在 session log 里无来源标记。

## 第七轮评审 — Q32 修正 + 定案

用户指出「web 和桌面端都需要面板，扫码等等」。

**核实结论**：桌面端 = Electron 外壳包着**完整的 Web 应用**（`docs/architecture.md:55`：「The Host invokes the shared CLI profile runner and **complete Web application**… activating client plugins in the same document」）。

⇒ **做客户端插件半边，web 与桌面端自动同时支持**。不需要写两套。

**修正记录**：我在上一轮错误地推荐 (b) Host 端 HTTP 面板并说 (c)「复杂度高一档、留到 v2」。正确结论是 **(c) 正规客户端插件**——它是唯一不用自己实现鉴权、且自动覆盖两端的做法。

### 鉴权问题的澄清（用户质疑「个人使用为啥需要鉴权」）

核实机制：
- `ctx.webServer` 本身「owns no TLS, authentication, or Origin policy」（`docs/subsystems/web-server.md:47`）
- DSH 自己的 `/api` 路由与 index → 由 `connection` 插件鉴权（`gateway` 注册 WS 路由时调 `connection.admit(req)`）
- **插件自己注册的自定义路由 → 默认无鉴权，DSH 不管**

⇒ 鉴权问题只在「自己开 HTTP 路由」时才存在。**走客户端插件半边则完全绕开**（走 DSH 已认证的客户端通道）。

### 最终定案

**Q32 = 正规客户端插件（设置页卡片）+ CLI 登录命令；不做独立 HTTP 面板，不自己做鉴权。**

### 构建成本（已向用户说明）

官方 `clientBundle` preset 在 `packages/client/tsdown.client.ts`，**不在已发布的 npm 包里** → out-of-tree 包必须自己复现：lazy-CJS factory 格式（`register(name, factory(require))`）、externals 处理、Indexed Source Map、revision。

新增事实任务 21bd96b2：查客户端插件的具体构建复现方案。

## 2026-10-15（续）— README 的安装指引三条全错

用户问「我该如何安装、实际使用」。这才第一次从零装一遍——**M7 只验过 tarball，
而 README 教的是 `add dsh-channel-wechat`**。实测三种方式：

| 方式 | 结果 | 原因 |
|---|---|---|
| `add dsh-channel-wechat`（README 原文） | ❌ **404** | 包从未发布到 npm（`npm view` → E404）。**README 的第一条指令对任何用户都跑不通** |
| `add github:...` | ⚠️ 能成但**首次必失败** | pnpm 拒绝执行 git 依赖的构建脚本，须手工加 `allowBuilds` 到 profile 的 `pnpm-workspace.yaml` 再重跑 |
| `add <本地目录>` | ❌ **静默装成空包** | 生成 `link:`，**`link:` 不跑构建**；`lib/` 被 gitignore → 启动 `failed to import`，**不加载也不崩** |
| `add <tarball>` | ✅ 干净 | `prepack` 自动构建 |

**两条实测钉住的机制**：

1. **`add` 会顺带把包写进 profile 的 `bundles`**。只进 `dependencies` 不进 `bundles` → 包装好却**永不加载**，`--dump-config` 一行都没有且不报错。桌面端 profile 正是被手工 `link:` 挂过，所以「装了却从不生效」。
2. **本地目录安装 ≠ 构建**。必须先 `pnpm install && pnpm build`，否则无 `lib/`。失败形状是 `failed to import`——看得出来，但**不看启动日志就会被当成装成功**。

## 2026-10-16 — 真机使用后修两个缺陷（0.1.1）

用户把 `0.1.0` 装到桌面端真实使用，**每条微信消息都失败**。两个缺陷，均已修复 + 红绿 + 变异验证。

### 缺陷一：DSH 核心包被装进 profile，分裂运行时

**症状**：插件加载正常、路由能响应（对照实测 `200` vs 不存在路径 `404`），但消息全失败：

```
inbound message failed: no agent factory registered (load an agent-loop plugin)
inbound message failed: cannot create effect on inactive context
```

**走了三条死路**（都像答案，都被推翻）：

| 假设 | 推翻依据 |
|---|---|
| `agent-loop` 依赖缺失 | 1308 行配置树里它存在、6 个提供者齐全 |
| 默认模型 `deepseek-flash` 不存在 | `agent-loop` 的 config 只有 `agents: []`，不读默认模型；且 GUI 自身能对话 |
| `desktop-host` 与 cli 行为不同 | **同一份配置**在隔离环境跑 cli，**正常创建会话并回复** |

**根因**：`dependencies` 里有 **`@deepseek-ai/schemastery`**（DSH 核心包）→ 被实体装进 profile。
**同版本、不同 inode 的两份副本**：

```
3.18.4  inode 12121912  profiles/desktop/node_modules/@deepseek-ai/schemastery
3.18.4  inode 12148791  profiles/node_modules/@deepseek-ai/schemastery   ← 官方闭包
```

`cosmokit`（cordis 的响应式底座）含 `Symbol.for("cosmokit.volatile.write")`；
插件持第二份 = **第二套模块图** → `ctx.effect()` 跨图 → factory 与 effect 状态不通。
**版本号一致，所以任何版本检查都发现不了，只有 inode 不同。**

**来源**：官方 **issues 已关闭**（只用 Discussions），但社区手册
[deepseek-harness-handbook](https://github.com/sandbaseai/deepseek-harness-handbook) 的
`duplicate-core-runtime-closure` 一条精确描述，原文明确写着
**「do not add DSH core packages as profile dependencies」**。

**修复**：`@deepseek-ai/schemastery` 从 `dependencies` → `peerDependencies`（+dev）。
修复后 profile 的 `node_modules/@deepseek-ai/` **为空**，只剩 `commander`。

**为什么 M7 没抓到**：当时只验「**tarball 装进全新 profile 能加载**」。
副本在全新 profile 里**照样会装进去**，只是没有真实对话去触发。
清单测试当时**只检查「用到的 import 都有声明」**，**从不问「哪些包不该进 profile」**。已补测试。

   `ModelDirectory`/`ModelDirectoryResolver`/类型，`ModelSelect` 组件**没有**再导出；它也不在壳的
   冻结模块表（`PLATFORM_MODULES` 恰好 9 项）。运行时 `require` 会抛
   “missed the module table”。`dsh.client.external` 是加载**另一个插件的 graph row**，
   `packages/client/AGENTS.md` 明说不是 feature plugin 的依赖机制。
   ⇒ **自建选择器**，但用 primitives 的 `Menu`——官方权限选择器就是这么做的。
2. **`agentDefaultModel.saveSelection()` 改的是全局默认**，会影响 GUI 新建的会话，与「只限微信通道」
   冲突。改用「创建时传 `agentOptions`，未配置则回退全局默认」，架构不变（本插件本来就在传）。
3. **权限有 per-session 公开 API**：`permissionPresets.set(session, name)`，webhook 是现成先例。
   `CreateAgentOptions` **没有**权限字段，所以只能在创建**之后**写。
4. **`danger-full-access` = sandbox 全开 + `approval: never`**，而 `never` 在 approval 服务内部、
   waterfall **之前**就判定 ⇒ 本插件 `prepend:true` 的审批卡**不会被调用**。
5. **宿主 `set()` 没有风险确认**：官方页的「Enable Full access?」勾选框是纯客户端 UI。
   ⇒ 确认必须由插件自己加。

### 实现

**批次 A（宿主）**：`Config` 加三个 volatile 字段 `provider`/`model`/`permission`；
模型经 `agentOptions` 传递（空对回退 profile 默认，**半填直接拒绝**而不是猜测）；
权限创建后 `permissionPresets.set`；新增 `GET /api/channel-wechat/models` 实时读 `ctx.llm`。

两个刻意的取舍：

- **扁平字段而非嵌套 `{provider, model}`**：`SettingsFormModel` 写的是**单段路径**（`path: [field]`），
  嵌套对象会渲染出一个**存不进去**的控件。
- **权限只在创建时应用**：已恢复的会话自带 durable 权限事件，包括用户用 `/permission` 中途改过的，
  `pinInitialPermission` 会恢复它们；resume 时再套用配置会**静默撤销用户自己的选择**。

**批次 B（页面）**：模型用 `Menu` 锚定下拉（选项来自新路由，实时）；权限用 `SegmentedControl` 三段；
选完全权限先弹 `RiskConfirmation`。

### 顺手修掉一个我自己引入的缺陷

行 id 最初写成 `provider + '/' + model`，再用**第一个** `/` 切开。模型 id 本身可能含斜杠
（`meta-llama/Llama-3`），那样会解出**错误的 pair**。官方注释明确说行 id 是「resolved by lookup,
never parsed」。改成 JSON 编码 + `decodeModelRowId` 校验（非本页产生的 id 一律拒绝）。

### 文档里的新工具事实（本次查清）

- 本机 npm **11.13.0 没有 `stage` 子命令**；`npm stage list/view/approve/reject` 属于
  **npm 12**（实测 `npx npm@latest stage list` 可用，需 `--cache` 绕过 `~/.npm` 不可写）。
- `/-/stage`（复数）**不存在**；`/-/stage?page=0&perPage=100&package=<name>` 才返回条目。
- `npm view` 会命中本地缓存，排查传播延迟时**不可靠**；认证查单版本才是准的。
