## 侦察报告 05 的关键结论（DSH 侧 channel 接入面）

**不存在 channel / connector / bridge seam**。微信 channel ≈ 自造三块：入站适配器 + 会话映射表 + 出站订阅转发器。

- **现成可复用**：`Agent.followup/steer/inject`（入站注入）；`ctx.commands.execute(agent, line, [], signal)`（命令分发，四参数签名 + 非 Web adapter 调用范式）；`ctx.agents.create({meta:{cwd}})`；`ctx.on('session/event')`；`ctx.on('agent/assistant-stream')`；`ctx.webServer.register`；`MessageSourceMap` 声明合并；`ctx.messageFeedback`（微信 👍/👎 可落此）
- **需自己造**：微信入站（登录/长轮询/验签 + 会话映射表）；微信出站（分段/限流/重试）；同会话串行与去重；主动推送触发器
- **明确不存在**：出站投递 seam / 投递目标抽象；**运行时切换 cwd**（`SessionHeader.cwd` immutable）；`webhookRuntime` 的 completion result

**对 Q8 的硬约束**：用户选「默认一个目录 + 工作目录用户可选」——但 **cwd 终生不可变，换目录必须新建 Session**。设计上应表达为「切换工作区 = 切换/新建会话」。

**必做项**：`declare module '@deepseek-ai/dsh-llm' { interface MessageSourceMap { wechat: {...} } }`，否则微信消息在 session log 里无来源标记。

## 第七轮评审 — Q32 修正 + 定案

用户指出「web 和桌面端都需要面板，扫码等等」。

**核实结论**：桌面端 = Electron 外壳包着**完整的 Web 应用**（`docs/architecture.md:55`：「The Host invokes the shared CLI profile runner and **complete Web application**… activating client plugins in the same document」）。

⇒ **做客户端插件半边，web 与桌面端自动同时支持**。不需要写两套。

**修正记录**：我在上一轮错误地推荐 (b) Host 端 HTTP 面板并说 (c)「复杂度高一档、留到 v2」。正确结论是 **(c) 正规客户端插件**——它是唯一不用自己实现鉴权、且自动覆盖两端的做法。

### 鉴权问题的澄清（用户质疑「个人使用为啥需要鉴权」）

核实机制：
- `ctx.webServer` 本身「owns no TLS, authentication, or Origin policy」（`docs/subsystems/web-server.md:47`）
- DSH 自己的 `/api` 路由与 index → 由 `connection` 插件鉴权（`gateway` 注册 WS 路由时调 `connection.admit(req)`）
- **插件自己注册的自定义路由 → 默认无鉴权，DSH 不管**

⇒ 鉴权问题只在「自己开 HTTP 路由」时才存在。**走客户端插件半边则完全绕开**（走 DSH 已认证的客户端通道）。

### 最终定案

**Q32 = 正规客户端插件（设置页卡片）+ CLI 登录命令；不做独立 HTTP 面板，不自己做鉴权。**

### 构建成本（已向用户说明）

官方 `clientBundle` preset 在 `packages/client/tsdown.client.ts`，**不在已发布的 npm 包里** → out-of-tree 包必须自己复现：lazy-CJS factory 格式（`register(name, factory(require))`）、externals 处理、Indexed Source Map、revision。

新增事实任务 21bd96b2：查客户端插件的具体构建复现方案。

## 2026-10-15（续）— README 的安装指引三条全错

用户问「我该如何安装、实际使用」。这才第一次从零装一遍——**M7 只验过 tarball，
而 README 教的是 `add dsh-channel-wechat`**。实测三种方式：

| 方式 | 结果 | 原因 |
|---|---|---|
| `add dsh-channel-wechat`（README 原文） | ❌ **404** | 包从未发布到 npm（`npm view` → E404）。**README 的第一条指令对任何用户都跑不通** |
| `add github:...` | ⚠️ 能成但**首次必失败** | pnpm 拒绝执行 git 依赖的构建脚本，须手工加 `allowBuilds` 到 profile 的 `pnpm-workspace.yaml` 再重跑 |
| `add <本地目录>` | ❌ **静默装成空包** | 生成 `link:`，**`link:` 不跑构建**；`lib/` 被 gitignore → 启动 `failed to import`，**不加载也不崩** |
| `add <tarball>` | ✅ 干净 | `prepack` 自动构建 |

**两条实测钉住的机制**：

1. **`add` 会顺带把包写进 profile 的 `bundles`**。只进 `dependencies` 不进 `bundles` → 包装好却**永不加载**，`--dump-config` 一行都没有且不报错。桌面端 profile 正是被手工 `link:` 挂过，所以「装了却从不生效」。
2. **本地目录安装 ≠ 构建**。必须先 `pnpm install && pnpm build`，否则无 `lib/`。失败形状是 `failed to import`——看得出来，但**不看启动日志就会被当成装成功**。

## 2026-10-16 — 真机使用后修两个缺陷（0.1.1）

用户把 `0.1.0` 装到桌面端真实使用，**每条微信消息都失败**。两个缺陷，均已修复 + 红绿 + 变异验证。

### 缺陷一：DSH 核心包被装进 profile，分裂运行时

**症状**：插件加载正常、路由能响应（对照实测 `200` vs 不存在路径 `404`），但消息全失败：

```
inbound message failed: no agent factory registered (load an agent-loop plugin)
inbound message failed: cannot create effect on inactive context
```

**走了三条死路**（都像答案，都被推翻）：

| 假设 | 推翻依据 |
|---|---|
| `agent-loop` 依赖缺失 | 1308 行配置树里它存在、6 个提供者齐全 |
| 默认模型 `deepseek-flash` 不存在 | `agent-loop` 的 config 只有 `agents: []`，不读默认模型；且 GUI 自身能对话 |
| `desktop-host` 与 cli 行为不同 | **同一份配置**在隔离环境跑 cli，**正常创建会话并回复** |

**根因**：`dependencies` 里有 **`@deepseek-ai/schemastery`**（DSH 核心包）→ 被实体装进 profile。
**同版本、不同 inode 的两份副本**：

```
3.18.4  inode 12121912  profiles/desktop/node_modules/@deepseek-ai/schemastery
3.18.4  inode 12148791  profiles/node_modules/@deepseek-ai/schemastery   ← 官方闭包
```

`cosmokit`（cordis 的响应式底座）含 `Symbol.for("cosmokit.volatile.write")`；
插件持第二份 = **第二套模块图** → `ctx.effect()` 跨图 → factory 与 effect 状态不通。
**版本号一致，所以任何版本检查都发现不了，只有 inode 不同。**

**来源**：官方 **issues 已关闭**（只用 Discussions），但社区手册
[deepseek-harness-handbook](https://github.com/sandbaseai/deepseek-harness-handbook) 的
`duplicate-core-runtime-closure` 一条精确描述，原文明确写着
**「do not add DSH core packages as profile dependencies」**。

**修复**：`@deepseek-ai/schemastery` 从 `dependencies` → `peerDependencies`（+dev）。
修复后 profile 的 `node_modules/@deepseek-ai/` **为空**，只剩 `commander`。

**为什么 M7 没抓到**：当时只验「**tarball 装进全新 profile 能加载**」。
副本在全新 profile 里**照样会装进去**，只是没有真实对话去触发。
清单测试当时**只检查「用到的 import 都有声明」**，**从不问「哪些包不该进 profile」**。已补测试。

   “missed the module table”。`dsh.client.external` 是加载**另一个插件的 graph row**，
   `packages/client/AGENTS.md` 明说不是 feature plugin 的依赖机制。
   ⇒ **自建选择器**，但用 primitives 的 `Menu`——官方权限选择器就是这么做的。
2. **`agentDefaultModel.saveSelection()` 改的是全局默认**，会影响 GUI 新建的会话，与「只限微信通道」
   冲突。改用「创建时传 `agentOptions`，未配置则回退全局默认」，架构不变（本插件本来就在传）。
3. **权限有 per-session 公开 API**：`permissionPresets.set(session, name)`，webhook 是现成先例。
   `CreateAgentOptions` **没有**权限字段，所以只能在创建**之后**写。
4. **`danger-full-access` = sandbox 全开 + `approval: never`**，而 `never` 在 approval 服务内部、
   waterfall **之前**就判定 ⇒ 本插件 `prepend:true` 的审批卡**不会被调用**。
5. **宿主 `set()` 没有风险确认**：官方页的「Enable Full access?」勾选框是纯客户端 UI。
   ⇒ 确认必须由插件自己加。

### 实现

**批次 A（宿主）**：`Config` 加三个 volatile 字段 `provider`/`model`/`permission`；
模型经 `agentOptions` 传递（空对回退 profile 默认，**半填直接拒绝**而不是猜测）；
权限创建后 `permissionPresets.set`；新增 `GET /api/channel-wechat/models` 实时读 `ctx.llm`。

两个刻意的取舍：

- **扁平字段而非嵌套 `{provider, model}`**：`SettingsFormModel` 写的是**单段路径**（`path: [field]`），
  嵌套对象会渲染出一个**存不进去**的控件。
- **权限只在创建时应用**：已恢复的会话自带 durable 权限事件，包括用户用 `/permission` 中途改过的，
  `pinInitialPermission` 会恢复它们；resume 时再套用配置会**静默撤销用户自己的选择**。

**批次 B（页面）**：模型用 `Menu` 锚定下拉（选项来自新路由，实时）；权限用 `SegmentedControl` 三段；
选完全权限先弹 `RiskConfirmation`。

## 2026-10-17（六）— 发布 `0.2.1`：版本号改为跟随 DSH，并修长轮询 teardown

### 为什么要改版本号规则

用户提出「版本号和 dsh 的版本号相应」。讨论后确定：**`<DSH 主>.<DSH 次>.<我们自己的补丁号>`**，
不带 `rc`/`alpha`；`0.2.x` 配 DSH `0.2` 那一代，**`x` 完全归我们**——DSH 发 `0.2.2` 我们
不改号，只有本插件自己有改动才 +1。

四段号（`0.2.1.1`）**不可行**，实测三种写法：

| 写法 | 结果 |
|---|---|
| `0.2.1.1` | **非法 semver**，`npm publish` 直接拒绝 |
| `0.2.1-1` | 合法但属**预发布**，npm 不会更新 `latest`，用户装不到 |
| `0.2.1+1` | 合法但 build metadata **不参与排序**，等于没加 |

三个数位装不下四组信息，只能取其一。**不追 DSH 的预发布号**——DSH 约 1–5 天一个预发布版
（`0.2.1-alpha.1` 10-03 → alpha.5 10-16 → rc.1 10-17），跟着编号会产出大量**内容为空**的版本。

### `engines.dsh`：只声明下界，刻意不设上界

`engines: { dsh: ">=0.2.0-rc.1" }`。DSH 一旦看到它就**只用它判定兼容性**，
`@deepseek-ai/dsh-*` 的 peer 范围不再参与（`packages/boot/app-boot/src/plugin-compatibility.ts:77-80`）。

**我一开始判断反了两次，都被实测推翻**：

1. 我说过 `^0.2.0` 能包含 `0.2.0-rc.2`。**错**：caret 挂在 release 上会排除同号预发布版。
2. 我说过加 `engines.dsh` 会限制高版本安装。**错**：不写它时走 peer 判定，`^0.2.0-rc.1`
   反而**更严**——它拒绝 `0.3.0`。`engines.dsh` 只能**放宽**。

| 写法 | `0.2.0-rc.2` | `0.3.0` | `1.0.0` |
|---|---|---|---|
| peer `^0.2.0-rc.1`（无 engines） | OK | **NO** | **NO** |
| `engines.dsh: >=0.2.0-rc.1` | OK | OK | OK |

**不上界的理由**：加了天花板，DSH 每发一个新版本、本插件未重发之前用户就**装不上**。
对通道插件，「立刻不能用」比「在未实测版本上跑」更糟。

**不加 peer 的理由**：实测 `^0.2.1-rc.1` 会**弄丢 `0.2.0-rc.2`**，而它正是 npm 上的 `latest`
**和打包桌面端**。且因 `engines.dsh` 已存在、peer 根本不参与判定，改 peer 对安装准入**零收益**，只有风险。结论：不动 peer。

### 修了一个真缺陷：长轮询没被中止

用户报桌面端更新失败：`Host did not complete graceful task teardown`。

**根因**：在飞的 `fetch` 没被 abort，配合 ref'd 的 `setTimeout`，事件循环不退出。
原实现只「race 一个超时」——那只释放**等待它的循环**，没中止**请求本身**。

`PollFn` 签名改为 `(cursor, timeoutMs, signal)`，`monitorLoop` 把 `options.signal` 传进 poll；
`src/wechat/api.ts` 的 `send()` 把 abort 转发给 fetch、`timer?.unref()`、在 `finally` 移除监听。

**实测**（服务端跑在独立进程）：改前 `loop ended at 114ms` 然后 `STILL ALIVE after ~10s`；
改后 `exited code=0 after 119ms`。

## 2026-10-17（七）— 发布 `0.2.2`：更新检查、Windows 路径修复

### 一、Windows 用户输不进工作目录（真机报告）

现象：在插件页把「工作目录」填 `D:\workspace\coding\dsh-ws`，下方立刻红字「必须是绝对路径」，
保存按钮禁用，**Windows 上任何合法路径都填不进去**。

根因在 `src/client/client.js` 的判定只有一行：

```js
return trimmed.charAt(0) === '/' ? ... : undefined;
```

它只认 POSIX 绝对路径。浏览器里没有 `node:path`，也不知道 Host 在哪个平台，
所以「什么算绝对路径」本来就得由这个文件自己决定——而它决定错了。

顺带查出同一假设的第二处：`src/bridge/deliverables.ts` 的 `resolvePath` 也不认盘符路径，
`D:\ws\out.xlsx` 会被拼成 `D:\ws\D:\ws\out.xlsx`。**这一处不报错，文件就是不发送。**

两处统一到 DSH 自己的规则（`packages/util/workspace-path/src/index.ts:17`
的 `isAbsoluteWorkspacePath`）：POSIX 绝对、盘符限定、完整 UNC 三种算绝对；
`D:foo`（盘符相对）与 `\foo`（会随进程当前盘变化）**继续拒绝**——会话 `cwd` 记录后不可更改，
把依赖进程状态的路径存进去等于埋一个搬不动的错。

拼接时分隔符改为跟随 cwd 自身写法，并处理 cwd 末尾已有分隔符（`D:\` 不会变成 `D:\\`）。

### 二、检查更新卡片（本轮主要功能）

需求：插件页能检查新版本、并给出可执行的更新方式。

**先做的是实测，不是写代码。** 在真实 web profile + 独立 `DSH_HOME` 上装 `0.1.3`，
进程内调 `pluginManager.installBundle('dsh-channel-wechat@latest')`：

```
{ "application": "failed", "error": { "code": "already-installed" } }
```

守卫在 `packages/boot/plugin-manager/src/index.ts:542-545`：**HMR 服务存在时**，
只要包已在 profile 的 dependencies 里就拒绝。而 HMR 在 base bundle 默认启用，用户关不掉。

再测官方页面「先卸再装」那条路（`manager-store.ts:688-704`）：

```
removeBundle → stage: remove, changed: true, application: failed,
                error.code: operation-error
```

失败后磁盘上的实际状态：

```
dependencies: { "dsh-channel-wechat": "0.1.3" }   ← 包还在
bundles: ["dsh-base", "dsh-web-app"]              ← 但已从 profile 摘除
```

**这是最坏的失败**：包还装着、插件从 GUI 消失、没有任何提示指向这个状态。
失败原因是 pnpm 的 `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`——`removeBundle` 内部
`runPnpm(['remove', name])` 不带任何 policy 参数。

**官方已有同一缺陷的报告**：deepseek-harness Discussion **#9936**
（「Desktop profile 上插件市场更新任何插件都失败」，报告人独立复现，2 参与者、无官方回应）。
我另装了当前最新的 `0.2.1-rc.2` 核对，**那行守卫一字未改**。

于是转去测 CLI 路径，两套独立 profile：

| 操作 | 结果 |
|---|---|
| `plugin add dsh-channel-wechat@latest` | **0.1.3 → 0.2.1 成功，bundles 保持 true** |
| `plugin remove dsh-channel-wechat` | **干净**：dependencies 与 bundles 一起清 |

**关键结论：CLI 路径不需要先 remove。** `pnpm add` 本身就覆盖旧版本，
CLI 上没有那道 `already-installed` 拦截。升级后 `--dump-config` 正确合成、
真实启动打印出监听地址。

所以最终形态：**页面只给命令，不代劳升级**。这是实测逼出来的，不是保守。

### 三、命令为什么是全路径

用户提问「能检测出是 PATH 启动还是绝对路径的」。实测 `process.argv0`：

| 调用方式 | `argv0` | `env._` |
|---|---|---|
| `node /path/x.mjs` | `"node"` | 绝对路径 |
| 经 PATH 裸名 | 绝对路径 | shim 路径 |

**无法稳定区分**，且区分出来也没用——用户当初的 PATH 现在可能已经变了。
所以直接给绝对路径：`process.execPath` + 从 `installAnchor` 推出的 `lib/bin.js`，
不依赖任何环境状态。

桌面 profile 必须换一种：`apps/cli/src/args.ts:84` 拒绝终端管理 `desktop`，
只有 App 自带 CLI（`apps/desktop-host/src/cli.ts:16` 设 `manageDesktopProfile: true`）能管。
所以桌面给 App 内的 carrier 路径；`process.resourcesPath` 不存在（非 Electron）时
返回 undefined，页面就**不给命令**——宁可没有，也不给一条会被拒的。

`--config.minimumReleaseAge=0` 是命令的一部分，不是可选项：不带它，用户更新到刚发布的版本

## 2026-10-17（八）— 检查更新改成按钮触发

### 一、问题

## 2026-10-17（九）— 修：保存配置后微信消息不再被回复

### 一、症状（用户报告）

| 时刻 | 动作 | 结果 |
|---|---|---|
| t1 | 设置一个工作区 | — |
| t2 | 发消息 | 正常回复 |
| t3 | 改工作区，保存 | — |
| t4 | 发消息 | **不被回复** |
| t5 | 在微信里 `/new` | 恢复正常 |

用户怀疑「微信会话被一个写入句柄占着」。方向对了一半。

### 二、复现与定位

先写出集成测试（`session-policy-wiring.spec.ts` 的 `still answers the next message after
a working directory change`），用真实 `apply`、真实 agent loop、stub 掉 `fetch`，在两次消息之间
调用 `fiber.update({ cwd: '/elsewhere' })` 模拟页面保存。**测试红了**，且日志里出现**两次**
`polling as: bot-1`。

接着用探针测三件事：

1. **volatile 更新会重新执行 `apply`**，但不卸载插件：
   ```
   MOUNT seen=[ 'apply' ] state=ACTIVE
   IMMEDIATELY state=UNLOADING
   AFTER 300ms state=ACTIVE seen=[ 'apply', 'apply' ]
   ```
2. **cordis 会等待异步 disposer**：
   ```
   LOG ["apply","dispose-start-1","dispose-end-1","apply"]
   ```
3. **但我们的 disposer 没等任何东西**：它只调 `run.stop()`，那是同步的、只发 abort。

于是根因有两层：

- 第一层：`SingleRun.stop()` 只 abort，不等待 run 结束。abort 是「请求停止」，不是「已经停止」。
  新旧两个 run 重叠，旧 run 仍持有该 peer 的会话和游标。
- 第二层（更根本）：**`Channel` 从来没读过 `options.signal`**。
  `runtime.ts:293` 把 signal 传进了 `Channel`，`Channel.run()` 却只用自己的
  `new AbortController()`。所以 abort 根本没被任何东西接收——旧 run 永远不停。

第二层是长期潜伏的缺陷，被第一层掩盖：以前 `run.stop()` 的返回值被丢弃，没人发现旧循环从不退出。

> 顺带：`~/Library/Logs` 之外，插件日志里 10-15/10-16 也有
> `channel stopped: ENOENT ... cursor.json.tmp -> cursor.json`——两个 run 同时写同一个游标文件，
> 正是同一个根因。这条证据在修之前就在，只是当时没被读懂。

### 三、修法

| 文件 | 改动 |
|---|---|
| `src/channel/channel.ts` | 读 `options.signal`，把外层 abort 转发进本地 controller（含已 abort 的情况） |
| `src/channel/single-run.ts` | `launch` 可以返回 promise；`start()`/`stop()` 改 async；`stop()` 等 run 结束；`force` 替换时先 `await stop()` |
| `src/index.ts` | `launch` 返回 `runChannel(...)` 的 promise；disposer `return run.stop()` 而不是丢弃 |

`Channel.stop()` 本身没改——它原本就会 `await this.running`，只是 `running` 之前永远不 settle。

### 四、测试

- 新增集成测试 1 个（上面那条），直接覆盖报告的四步。
- `tests/unit/single-run.spec.ts` 新增 1 条：**替换必须等旧 run settle**，用 `order` 数组断言
  顺序是 `launch1 → aborted1 → settled1 → launch2`，并在替换发起后立刻点一次微任务，确认
  `launch2` 尚未开始。
- 原有两条测试因 `start()` 变 async 而修正（加 `await`），不是断言放宽。

### 五、变异验证（如实记录）

| 变异 | 结果 |
|---|---|
| `Channel` 忽略 `options.signal` | 整个文件挂死（`dispose` 永不返回）→ **被捕获** |
| disposer 改回 `void run.stop()` | **未捕获**，测试仍通过 |

第二条如实记录为**未被测试固定**：它只在「旧 run 的 teardown 还没跑完、新 run 已经开始」的窄窗口里
出问题，而 `Channel` 接收 signal 之后这个窗口已经很小。修它仍然是必要的（`SingleRun` 的语义本该
如此），但**不能声称有回归测试守着它**。

### 六、被这次修复暴露的一个测试缺陷

`channel.spec.ts` 的 `reaches the right agent for a native command after a rotation`
在 `ctx.fiber.dispose()` **之后**读 `live` 映射。以前 dispose 不等 teardown，映射还有内容；
现在等，映射已空，断言变成 `[{...}] to deeply equal [undefined]`。

修的是测试而不是实现：在 dispose 前把期望值取下来，并把断言从 `toEqual([map.get(...)])`
改成 `toBe` + `toBeDefined()`——原来那种写法在两边同为 `undefined` 时会**假通过**。

## 2026-10-17（十）— 0.2.2 仍然退不掉：signal 修复没进发布

### 一、报告与实测的落差

用户报 0.2.2 上关桌面端仍出现：

```
Host did not complete graceful task teardown
(exit null, signal SIGTERM, shutdown acknowledged true, graceful deadline exceeded true)
```

上一轮我判断「已经修了」。这个判断**错在版本对齐**：实测发现

| 提交 | 是否在 `v0.2.2` 里 |
|---|---|
| `d9fd11a`（把 signal 传进 poll / unref 请求定时器） | **在** |
| `54e130c`（`SingleRun.stop()` 等待收尾 + `Channel` 读 `options.signal`） | **不在** |

用户装的就是 0.2.2，npm 上 `dist-tags.latest` 也是 0.2.2，`versions` 里没有 0.2.3。
所以问题当然还在。

### 二、根因：`d9fd11a` 在 0.2.2 里是空修复

`git show v0.2.2:src/channel/channel.ts` 的 `run()` **只用自己的 controller**，从不读 `options.signal`：

```ts
const controller = new AbortController()
this.controller = controller
this.running = monitorLoop({ ..., signal: controller.signal })
```

`runtime.ts` 明明把 `options.signal` 传进了 `Channel`，但那条信号在 `run()` 里被丢掉了。
于是 `SingleRun.stop()` 的 `abort()` 打到 `controller` 之外的空气上，`monitorLoop` 收到的是
`controller.signal`——一个外部够不着的 controller。

后果链：abort 传不进去 → 35 秒长轮询继续 → `run()` 永不 resolve → `Channel.stop()` 永不执行
→ 长轮询的 socket 撑着事件循环 → 过了 10 秒被 SIGTERM。

`d9fd11a` 把 signal 一路传到 `api.getUpdates` 是**对的且必要的**，但上游没人给它值，
所以没有行为变化。

### 三、实测对照（这是本轮的核心证据）

假网关跑在**独立进程**（否则 `server.listen` 自己就撑住事件循环，测不出东西——
第一版探针就错在这里，已废弃）。同一条路径，两种接线：

| 接线 | teardown 后进程退出 |
|---|---|
| 0.2.2（`Channel` 不读 signal，`stop()` 不可达） | **卡满 10000ms**，`graceful deadline exceeded` |
| HEAD（`Channel` 转发外层 abort） | **167ms 退出，exit 0** |

`reply.ts` 的重试 sleep 单独测过：默认参数下不带 `unref` 时进程在 teardown 后**多活 2002ms**
（`maxAttempts` 3 → 两次 1 秒间隔）。

### 四、修了什么

| 文件 | 改动 |
|---|---|
| `src/bridge/reply.ts` | 重试 `setTimeout` 加 `unref()`：2002ms → 1ms |
| `src/channel/monitor.ts` | idle sleep 加 `unref()`，空闲暂停不该撑住进程 |
| `tests/integration/channel-real-loop.spec.ts` | **新增**「owner abort 必须让 run settle」 |

`Channel` 读 `options.signal` 与 `SingleRun` 等待收尾本来就在 HEAD 里（`54e130c`），
这次没有重复改，只是补上了守着它们的回归测试。

### 五、变异验证

| 删掉 `Channel.run()` 里的 signal 转发（回到 0.2.2 行为） | **被捕获**——新测试挂死 120s，正是线上症状 |

这次和上一轮（九）不同：那条「disposer 不等收尾」的窄窗口仍然没有测试固定，
但**这次新增的测试真的会失败**，不是假通过。

### 六、为什么之前没测出来

`tests/unit/channel.spec.ts` 不存在；构造 `Channel` 的测试**没有一个**传 `signal`。
这正好命中本仓库已记录的复发缺陷模式：单测自己注入协作者，于是没有测试观察真实接线。

### 二、`/help` 挤成一行：不是换行丢了，是它本来就按 markdown 渲染

现象：微信里 `/help` 是一整行，把文本复制出来却有换行。所以字节是对的，是显示端把它折叠了。

微信按 markdown 渲染回复，**单个 `\n` 是软换行，会被折成空格**，只有空行才另起一个块。
上一版用 `\n` 拼清单，还把对齐寄托在一串空格上——markdown 同样会吃掉连续空格，
所以分列对齐和换行一起消失。

改成**每条之间空一行**、分隔符用破折号。`/help` 在 `channel.ts` 里就被拦下，不会发给模型，
所以排版不花 token。

上游 `@tencent-weixin/openclaw-weixin@2.4.10` 对每条回复都过一遍 `StreamingMarkdownFilter`
（保留代码块、表格、`**加粗**`、行内代码，剥掉中日韩斜体和图片语法）。这确认了渲染是 markdown，
也确认发送路径没有在协议层篡改文本：`sendText` 把 `params.text` 原样放进 `text_item.text`。

### 三、`/model` 写哪个存储，是这次最需要想清楚的决定

两个存储长得很像但不是一回事：

| | 谁读 | `/model` 是否写 |
|---|---|---|
| 本插件的 `channel-wechat.provider` / `.model` | 本插件的 create 与 resume，作为 `agentOptions` | ✅ |
| `ctx.agentDefaultModel` | GUI 自己新建的会话 | ❌ |

宿主自己的 `selectModel` **无条件**写 `agentDefaultModel`（`packages/api/session-controller/src/commands.ts:177`），
所以那条路一定会在微信用户切换时改掉 GUI 的默认模型。这里只写插件自己的两个字段，
代价小得多。

**我一开始写错了生效范围，且错误来自读代码而不是实测。** 请求 seed 是
`requestHeaderLogged ? requestProposal(persistedHeader) : { ...route }`，看起来 resume 会沿用会话里记录的模型。
但 `requestHeaderLogged` 是**每个 loop 实例**的字段、初值 `false`，所以新的 loop 首次请求取的是声明的 route。

实测探针（create → 一轮 → 在同一份日志上起新循环，要求换模型）：

```
REQUESTS: [{"provider":"first","model":"first-model"},
           {"provider":"second","model":"second-model"}]
```

`agentOptions` 赢了。所以写入配置 → 重跑 `apply` → 下一条消息就换模型，**不需要 `/new`**。

### 四、写入必须 detach：await 会自死锁

```
/model 命令运行中 → configEditor.edit() 触发 reload → dispose 本插件行
→ 该行的 disposer await Channel.stop() → stop 等所有在飞命令 → 等 /model 返回
```

`Channel.stop()` 用 `Promise.allSettled([...this.commandWork])`（`src/channel/channel.ts:354`），
而 `/model` 就在 `commandWork` 里。所以 `void editor.edit(...)` 是**构造上的必需**，不是风格选择。

用户能据以行动的校验（这个模型在目录里吗）仍然 await，打错字仍会当场收到回复；
只有写盘本身是 detach 的，失败进日志。

变异证据：把 `void editor.edit` 改回 `await`，集成测试**挂住**而不是干净失败——因为挂的是
`afterEach` 里的 `channel.stop()`，正是真实环境里 Host 报
`graceful teardown failed` 的同一处。

## 2026-10-19（二十）— 长期运行、会话级提权与输入状态

用户提出三件事：通道会不会自己停、审批卡能不能直接提权、能不能显示「正在输入中」。
调研结论先写进 `spec/20261019-channel-runtime-and-typing.md`，再按 TDD 逐项实现。

### 一、24 小时运行上限：一个从未被覆盖的默认值

`monitorLoop` 的 `DEFAULT_MAX_RUN_MS` 是 24 小时，而 `src/index.ts` **从未传过 `maxRunMs`**。
于是通道在启动满一天后**正常 `return`**，没有任何错误——从用户侧与「今天没人说话」无法区分，
而 `SingleRun` 保留了 `current`，`live()` 继续返回 `true`。

**起草期的判断被实测推翻**：文档先写「插件页保存配置不能恢复」，理由是 `WeakMap<Context, SingleRun>`
缓存会拿回旧实例。实际跑 `session-policy-wiring.spec.ts` 的 volatile 变更用例时，
stderr 出现两次 `polling as: bot-1`——先 dispose 再重跑 `apply` 就能恢复。原判断已在该文档里
标注为「一次判断被推翻并实测更正」。

修法两条，分开提交：`DEFAULT_MAX_RUN_MS = Infinity`；`SingleRun` 在 launch settle 时按 controller
身份清理槽位（防止自然结束的运行挡住后续启动）。

### 二、审批卡的第三个选项

用户裁定个人使用、不做二次确认，因此**选项文案是唯一风险告知**，必须同时写清
「之后不再弹审批卡」（`danger-full-access` 捆绑 `approval: never`）和「`/new` 恢复」。

两个顺序约束是这一项的核心：

1. **先 `settle` 再改权限**。`settle` 的返回值就是竞争的裁决；先提权会让一条没生效的回答也放宽会话。
2. **session id 经 `ctx.agents` 解析成活着的 session 对象**。卡片带到的是 id，而 `permissionPresets.set`
   要 session；那一轮可能在作答前就结束了，此时必须报失败，不能退化成「当前会话」。

`/new` 不需要改动：`applyPermission` 本来就只在 `resumed === false` 时调用。

### 三、输入状态

协议要求先 `getconfig` 拿 `typing_ticket`，再带票据 `sendtyping`。官方客户端每 5 秒续期，
这就是「一次上报不会常亮」的证据，本次沿用。

三处刻意的降级：票据为空、获取失败、上报被拒——一律不显示，且不影响回复。
上报被拒还会**主动 `invalidate`** 缓存（官方没有这一步），因为那是票据在 TTL 之前失效的唯一证据。

`start` 放在命令与卡片回复的提前 `return` 之后；`stop` 放在 `finally`，否则失败的一轮会留下
「正在输入」的假象。

`notifyStart` / `notifyStop` 经用户裁定**不做**：它是账号在线状态上报，不是输入状态，
缺了它通道照常收发，具体服务端影响没有实测证据。

## v0.2.6：`/h` 别名、`/skills`、`/cwd` 工作目录切换（2026-10-21）

### 一、`/h` = `/help`

手机键盘上 `/h` 比 `/help` 省事，加个别名是一行命令表加一个 `case` 分支的事。

### 二、`/skills` 只列名称

只列 `userInvocable` 的：只给模型用的技能没法从聊天里调用，列出来等于承诺一个做不到的操作。
查找上下文把 `cwd` 和 `scope: agent` 都传给 `ctx.skills.list`，与 DSH 自己的 `tool-skill`
pre-step 监听器完全同形——否则列出的集合会和模型看到的不一致。

部署没挂 `@deepseek-ai/dsh-skill` 时命令报「没有技能注册表」，与「注册表存在但没有技能」区分开：
只有后者是装个技能能解决的。`skills` 走 `ctx.get()` 而不是 `inject`，否则 headless 组合会整行 parking。

### 三、`/cwd`：换会话，不是会话内 `cd`

**这是本轮唯一需要拍板的设计，用户选了「方案 B」。** 详见 plan-v1 §Q53。

先说清为什么不用 `ctx.workingDirectory.set`（DSH 0.2.1-alpha.2 起有）：`sandbox-policy` 的
`workspaceRoot` 读 `session.header.cwd`，不读 workingDirectory。所以会话内 `cd` 之后，
`workspace-write` 下的写操作仍按**旧**边界判定——用户会看到「切过去了但写不了」，且是静默失败。
把「先放宽到 danger-full-access」当成功能前置条件是不能接受的。

换成「结束当前会话 + 在新目录新建」，没有半截状态：新 header 的 `cwd` 就是新目录，
`{{cwd}}`、沙箱、文件工具、presented 相对路径全部自洽。

**实现**：

- `PeerSessionStore` 增加 `cwds` 字段，与 `peers`（代次）同文件、同一读-改-写队列。
  两个字段共用一个 JSON 文档，分两次写会互相覆盖，测试用两个方向的并发用例钉住了这一点。
- `PeerMap.startNewIn(peerId, path)`：先记目录、再推进代次。顺序反了会有一个窗口让下一条消息
  在**旧**目录下创建新 id 的会话——而 header 改不了。
- `PeerMap.startNew` 现在自己调 `forget`：旋转后还留着旧 handle，`cwdFor` 会从正在结束的会话
  回答。原来由调用方负责，这次收进 `startNew` 更不容易漏。
- `src/channel/directory.ts` 单独放校验（绝对、存在、是目录、realpath）。拆出去一是因为
  `channel.ts` 已 694 行，二是因为它值得有自己的测试文件。
- `/new` 现在报告新会话的工作目录；`/cwd` 不带参数时报告当前目录。header 改不了，
  用户必须能确认自己在哪。

### 四、一个被测出来的时序问题

`createSession` 里为解析 cwd 加的那个 `await` 让 `tests/unit/runtime.spec.ts` 的回复用例在**全量**
运行里失败、单独运行却通过。原因是那个 bench 的 `whenIdle` 在订阅建立之前就被调用了，
多一个 await 改变了时序。

第一版修法是「没配 store 就走同步路径」，但那是治标：它让行为依赖「部署有没有配 store」。
真正的问题是**不该在没人切换过目录时引入额外 await**。最终写法按状态判断：

```ts
const switched = this.currentCwd.has(peerId) || this.generations?.cwd !== undefined
const cwd = switched ? (await this.cwdOf(peerId)) ?? this.cwd : this.cwd
```

这样没切换过的 peer 走的是和改动前**完全相同**的路径，多出来的异步只发生在真正用 `/cwd` 之后。

## 2026-10-22 — 微信里「一句话挂个冒号就没了」的根因与修复

### 症状与实测证据

用户反馈：微信里收到的回复很多是「一句话 + 冒号，后面什么都没有」。

解压真实会话日志（`~g11`，1.68 MB，1815 个 zstd 帧）后逐条统计 391 个 `assistant/message`：

| 分类 | 条数 | 以冒号结尾 |
|---|---|---|
| 文本 + **同一事件含 `tool-call`** | 46 | **40** |
| 纯文本（一轮的最终回答） | 7 | **0** |

结论：冒号结尾的 40 条**全部**是「调工具前的旁白」，正文是随后的工具参数——那些参数永远不会被发送。
按轮次看，turn 8（推送分支那轮）在 9 分钟里发了 18 条：17 条旁白 + 1 条 1225 字的结论。

### 缺陷一：旁白被当成回答发送

`extractAssistantText` 只挑 `type === 'text'` 的块拼接，**不看同一事件里有没有 `tool-call`**。
而 DSH 每走一步就提交一个 `assistant/message`（turn 5 有 193 个），于是每一步的引导语都被当回答发了。

改法：同一事件含 `tool-call` 块 → 返回 `undefined`。一轮结束时模型必定提交一条纯文本消息
（8 轮全部如此），所以不会漏结论。代价是被 `/stop` 中断的轮次什么也不发——那轮本来就没有结论。

**测试锁住了缺陷**：`reply.spec.ts` 原本断言 `[{tool-call}, {text:'done'}]` → `'done'`，把这个行为
当成正确语义。这条断言是「观察到的现状」而非「想要的语义」，缺陷因此长期不可见。

### 缺陷二：`ret: -2` 被当普通失败，1 秒重试 3 次后静默丢弃

通道日志与 session 记录**秒级对齐**：

```
08:15:43  FINAL "两件事都做完了。…"（1225 字）
08:15:44  turn/end {"kind":"completed"}
08:15:45  日志最后一行：reply to … failed: sendmessage: -2 prepare failed
```

`maxAttempts=3` + `retryDelayMs=1000`：08:15:43 发起，1 秒后重试，2 秒后再试，**08:15:45 放弃**。
限流窗口以秒到分钟计，1 秒后重试必然还在窗口内——三次全打在墙上。

`docs/recon/08` 早已记录参考实现的做法：识别「HTTP 200 + `ret:-2` + prepare failed」为限流，
指数退避 2s→16s / maxAttempts=5，外加 `paceSend` 保证间隔 ≥2000ms。本仓库一样都没实现。

改法：
- `isThrottled()` 按 `code === -2` 识别，**独立预算** `maxThrottleAttempts`，退避 2s→4s→8s→16s；
- 同 peer 发送调速 `minSendIntervalMs`（默认 1000ms），主动避免而不是事后发现；
- `BusinessError.code` 从私有构造参数改为公开字段，桥接层不必 import 协议层。

### 缺陷三：完全没有长消息分片

`docs/design.md` 把「消息分片」列为 v1 必需项，`recon/01` 写「自实现 4000 切分」——**源码里不存在**。
`sendText` 把整段文本塞进一个 `text_item`，传输层会**拒绝**超长 body 而不是截断，微信又没有重放，
所以超长回答会整条丢失。本轮回答 1200–2400 字都在 4000 以下，是运气不是设计。

新增 `src/bridge/split.ts`：按段落 → 行 → 句子 → 子句 → 空白依次尝试断开，上限默认 2000
（低于两个参考实现的 4000/2000）；跨切分的代码围栏在一段末尾补闭合、下一段开头补重开。

### 缺陷四：`credentials.listRecords` 缺失导致通道反复崩溃

10-22 日志有 4 次 `channel stopped: credentialsOf(...).listRecords is not a function`。
类型声明里有这个方法（`dsh-credentials/lib/types/index.d.ts:174`），宿主挂载的实例没有——版本错配。
`runChannel` 在 `listAccounts` 就抛，整个通道起不来。

改法：`listRecords` 改为可选，缺失时 `listAccounts` 返回空列表。记录操作仍可用，登录仍有效——
只是无法遍历发现。这比让通道崩溃诚实得多。

### 缺陷五：`stop()` 先 drain 再等轮次，会吞掉正在结算的回复

原顺序：`commandWork` → `replies.drain()` → `running`。turn 的 `assistant/message` 在 drain
**之后**才提交，回答被塞进一个再也没人等的队列，进程退出即丢失。「先 drain 更安全」是错的。

改为：`turnWork` → `commandWork` → `drain()` → `running`。

**`running` 必须放最后**：abort 之后循环还要走完当前一轮 poll 才返回，把它放最前面会让每次 stop
都白等一个轮询周期，而要 flush 的回复正排在那之后。这个错误顺序是我第一版改法，被 `runtime.spec.ts`
抓了出来。

### 缺陷六（自己引入又自己抓到的）：抽模块改变了微任务时序

为了让 `channel.ts` 回到 700 行以内，我把 `prepareMedia` 抽成 `media-prep.ts`。代码完全等价，
但多了一层 `async` 委托 —— 于是**无媒体时也多了一个挂起点**，入站消息投递被推后一个微任务，
`whenIdle` 提交 `assistant/message` 的时机随之改变，`runtime.spec.ts` 的回复测试立刻变红。

修法：`prepareMedia` 内联回 `channel.ts`，无媒体时**在任何 `await` 之前返回**。最终 695 行。

**教训**：抽模块时「行为等价」不等于「时序等价」。生产代码的异步边界是契约的一部分，
这次是测试替我发现的，不是我看出来的。

**这条测试的变异验证踩了两次坑**：前两版在错误顺序下也能通过，因为 (a) 末尾仍保留了第二次 drain，
(b) `send` 是同步的，发送在同一批微任务里就完成了。把 `send` 改成真异步（含 `setTimeout`）后，
变异才变红。**测顺序必须让被排序的副作用真的异步。**

### 验证

```
pnpm exec tsc --noEmit                                            → exit 0
pnpm exec vitest run --project unit                               → 49 files / 679 passed, 2 skipped
DSH_PACKAGED_SHIM=... pnpm exec vitest run --project integration   → 10 files / 108 passed
```

变异验证（5 处，全部被捕获）：

| 变异 | 变红的测试 |
|---|---|
| 去掉 `tool-call` 判断 | `does not send a message that also calls a tool` |
| 限流分支失效 | 3 条 throttled 测试 |

## 2026-10-28 — 交互卡：自定义回答、`/stop` 撤卡、串行显示

用户提出三点：提问卡想能写自己的答案、`/stop` 要能终止所有审批、多张卡同时出现时不好用。

### 发现的真实缺陷（不只是缺功能）

**`/stop` 之后卡片是僵尸，而且会撒谎。** `agent.cancel()` 让那一轮的工具信号 abort，
DSH 内部把审批判成 `cancelled`、提问判成 `ASK_ABORTED` —— 但 `PendingCards` 不监听 signal，
条目还留着。用户之后回 `P1 1`，`settle()` **成功**，插件回「已收到，正在继续」。
那一轮早就结束了，这句话是假的。卡片要等 30 分钟超时才消失。

**串行显示缺失时的一处连带问题**：`resolveCardId` 只查「卡是否开着」，不查「是否已显示」。
串行之后，排在队里的卡也是开着的，`P2 1` 会被当成有效作答。

### 改动

| 项 | 做法 |
|---|---|
| 提问卡自定义 | `parseCardReply` 额外返回 `raw`（id 之后的原文），因为 `selections` 按空白切分会把「use a softer blue」拆成四个 token |
| 判定规则 | **一段全数字才是选项编号**，否则整段即 `custom` |
| 多题分隔 | 换行 → `\|` → 空白，取第一个能切出「正好每题一段」的 |
| `0` = 换到对话 | 卡片级选项，整张卡作废；新增 `CardHandedBackToChat`，message 说明用户想讨论 |
| `/stop` | `watchAbort` 监听 `req.signal` + `withdrawAll(peerId)` 显式清理；回复带作废张数 |
| 串行显示 | `CardService` 内 per-peer `PeerRun { waiting, shown, settled }`，队首才 `send` |
| 超时起算 | `offer({ arm: false })` + `arm()`，显示时才计时 |

**为什么闸门做在卡片层而不是借用 `peers.runExclusive`**：卡片回复必须绕过 peer 队列，
否则提问的那一轮正持有队列，回复永远到不了（既有不变量，见 `docs/invariants.md`）。

### 一处顺序修正（集成测试抓出来的）

`/stop` 最初写成「先 `cancelRunning()` 再 `cancelCards()`」，集成测试断言「1 张」却得到 0 张。
原因：`agent.cancel()` **同步** abort 信号，signal 监听已经把卡撤了，计数自然是 0。
改成**先撤卡再取消**。两种顺序结局相同（审批 `cancelled`、提问 reject），所以换序安全。

### 评审后的修正（同一轮）

独立评审跑完后发现 4 个真缺陷，都是我自己没测到的，已修并补测试：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| `addressesCard` 只认已显示的卡 | **最严重**。它决定是否绕过 peer 队列，返回 false 就让排队卡的回复走进 `runExclusive`，排在那轮正等的 turn 后面——于是我写的「还没轮到」提示**永远发不出去** | 拆成两个谓词：`addressesCard` 认所有未结算的卡（绕过队列），`answer()` 内部再用 `isShown` 决定能否作答 |
| 确认文案排在下一张卡之后 | 用户先看到新问题，再看到「已收到」 | `release()` 之前先 `await send(回执)` |
| 一次 abort 刷屏所有排队卡 | 一轮的 signal 是共享的，abort 同时跑完所有监听器，在监听器里直接显示 = 全部卡涌出后立刻被撤 | `CardQueue.schedule` 用 `queueMicrotask` 合并，且 `scheduled` 标志防重入 |
| `dispose()` 不清 `runs` | 复用同一个 service 时 `shown` 指向已删的卡，之后**一张都不显示** | `display.clear()` |

另有两处顺序修正：`onExpired` 先提示再推进（作废说明要排在替代卡之前）；
`shareWithGui` 下 GUI 赢时发一条「已在 Harness 界面处理」，否则卡片凭空消失。

**自己测试的教训**：我曾把「排队卡不可作答」写成 `addressesCard('P2 1') === false` 的断言，
等于把 bug 当成规格固化了。真正的规格是「不可**接受**，但必须**识别**」——
两者的区别只有看 `channel.ts` 怎么用这个谓词才看得出来。

`src/bridge/card-queue.ts`（228 行），主文件回到 602 行。
