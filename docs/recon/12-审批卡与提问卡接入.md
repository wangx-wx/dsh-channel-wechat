## 1. 审批卡 `ctx.approval`

### 1.1 API 面

`ApprovalService extends Service`，`super(ctx, 'approval')`（`:150-156`）

| 成员 | 签名 | 位置 |
|---|---|---|
| `request` | `async request(req: ApprovalRequest): Promise<ApprovalOutcome>` | `:215` |
| `setPolicy` | `setPolicy(agent, policy): void` | `:184` |
| `overrideOf` | `overrideOf(session): ApprovalPolicy \| undefined` | `:252` |
| `ApprovalPolicy` | `'ask' \| 'never'` | `:67` |
| `ApprovalOutcome` | `'allowed-once' \| 'rejected' \| 'cancelled' \| 'unavailable'` | `types.ts:32` |

`ApprovalRequest`（`:111-132`）= `ApprovalRequestEvent` + `agent: Agent`、`toolName`、`callId?`、`reason?`、`signal?`。
⚠️ `displayReason` 只在 `ApprovalRequestEvent` 上，**只用于本地化呈现、不写审计日志**。

### 1.2 ★ 渲染与提交：**不走 `ctx.approval`**

`ctx.approval.request()` 是**提问方（asker）**的入口。外部通道是**回答方（answerer）**，走 **waterfall 监听器**：

```ts
ctx.on('approval/request', async (req, next) => { ... }, { prepend: true })
```

事件签名（`types.ts:87-91`）：
```ts
'approval/request'(
  this: Scoped<Agent>,
  req: ApprovalRequestEvent,
  next: () => Promise<ApprovalOutcome>,
): Promise<ApprovalOutcome>
```

- **渲染 = 注册监听器**
- **提交决定 = 从监听器 return 一个 `ApprovalOutcome` 字符串**，或调 `next()` 委托
- 返回 `'allowed-once'` 是唯一授权；非法值被规范化成 `'unavailable'`（`:285-292`）

⚠️ **`req` 里没有审批 id** —— id 是 `request()` 内部 `randomUUID()` 生成的（`:224`），只出现在 `session.append('approval/asked', ...)`（`:225-230`）。**answerer 拿不到 id**，只能靠 `req.callId` 或自造 id。

⚠️ 但 `req.agent` 是**完整的 live `Agent` 对象**，有 `agent.session`、`agent.ctx`。

### 1.3 是 waterfall；**无 `@Remote`**

- `@mode waterfall`，实现 `this.ctx.waterfall(scopeTarget(req.agent, req.agent), 'approval/request', req, () => Promise.resolve('unavailable'))`（`:281-284`）
- 不调 `next()` 即否决整条链
- `grep "Remote(" user-approval/src/index.ts` **退出码 1（无命中）**
- 能跨进程只因为 `approval/request` **事件**在白名单里（见 §4）

### 1.4 「谁先答谁生效」的真相：**DSH 不提供竞速**

- **Host 进程内多个 answerer 天然串行** —— 后一个只有在前一个调 `next()` 时才被调用
- **Web 路径**：Gateway 把**同一个** pending waterfall 分发给每个 Client，谁先回谁赢
  - `gateway/src/index.ts:589` 对每个 client `deliverRemoteEvent`
  - `receiveRemoteEventResult` 先 `removeRemoteEventDelivery`（`:605-609`）再 `settleRemoteEvent`（`:611-615`）
  - `finishRemoteEvent` 会 `pendingRemoteEvents.delete(pending.id)`（`:633-646`）
  - 迟到的结果命中 `pending === undefined` → **幂等 no-op**（`:603-604`）
  - 赢家结算时所有挂着 delivery 收到 `{ type: 'cancel' }` 帧（`:644-655`）
- ⚠️ **后答者的用户视角后果**：Web 侧卡片被 `cancel` 收起，**没有任何提示说明是谁先答的**。想给用户回执，**必须自己造**。

### 1.5 超时/取消

- **seam 内无任何超时** —— `grep "setTimeout|timeout"` 退出码 1。**默认无限等待**
- 终止条件：`req.signal` abort → `'cancelled'`（迟到 answer 被构造性丢弃，`:293-306`）／某 answerer 返回／无人接受 → 兜底 `'unavailable'`（**fail closed**）／answerer 抛错或返回非词汇值 → `'unavailable'`
- ⚠️ `request()` 要求**当前有未关闭的 turn**，否则 throw（`hasOpenTurn()` `:84-92`，前置检查 `:217-223`）

## 2. 提问卡 `ctx.userQuestions`

### 2.1 签名

```ts
async ask(request: AskUserQuestionRequest): Promise<AskUserQuestionAnswer>   // :86
```
- `AskUserQuestionRequest = { questions; agent?; signal? }`（`types.ts:70-77`）
- `AskUserQuestionItem = { id, question, detail?, header?, options?, multiSelect?, intent? }`（`:36-51`）
- `AskUserQuestionAnswer = { answers: { id, selected, custom? }[] }`（`:53-67`）
- 错误码：`EMPTY_QUESTIONS`/`BAD_INTENT`/`NO_PROVIDER`/`ASK_ABORTED`/`CALLER_NOT_LIVE`/`DELEGATED_CALLER`

### 2.2 与审批卡**完全同构**

`ctx.on('user-questions/request', (request, next) => ..., { prepend: true })`，返回 `AskUserQuestionAnswer` 即认领。

⚠️ **同样没有请求 id** —— 必须自造。
⚠️ **提问卡连 callId 都没有**（除 `intent.callId`，且**仅 `plan-review` intent 才有**）。`ask_user_question` 工具普通提问**完全不传 callId**。

### 2.3 ★ 澄清一个误读高发区

`ask()` 校验 `agents.get(agent.id) !== agent` → `CALLER_NOT_LIVE`，`roots().includes(agent)` → `DELEGATED_CALLER`（`:93-107`）。

**这对通道插件意味着什么**：
1. `ask()` 是**提问方** API。通道插件是**回答方**，**不需要持有 agent，也不需要调 `ask()`**。所以这两个错误码**对「接入提问卡」本身没有约束**
2. `request.agent` 一定存在且必然是 live root agent；通道插件**全程被动接收**
3. **真正的风险**：通道插件若**跨 turn 缓存 `agent`/`session` 对象**（如为 sessionId→用户映射），这些引用会在 dispose 后失效。`agents.get(id) !== agent` 的教训是：**id 相同不等于对象相同**。**缓存必须存 id，每次重查**

### 2.4 Web 侧怎么接的

`client/ui-user-questions/src/client/index.ts:105-107` 用 **`ctx.remote.$on`**（不是 `ctx.on`）。

- 编译期：类型投影把键限死在 `API_REMOTE_FORWARDED_EVENTS`
- 运行期：`ClientRemoteEvents.subscribe` **不做白名单校验**；**真正的闸门在 Host** —— `api-remotes/src/index.ts:48-72` 只为白名单事件注册转发 listener
- 硬约束（`api-remotes/src/index.ts:62-67`）：转发的 scoped waterfall 请求**必须把 agent 作为 `request.agent` 直接携带**，否则 Host 抛 `TypeError`

### 2.5 ★ 这个机制第三方插件能否复用？—— **不能**

1. **`registerRemoteEvents` 全进程只能调一次**：`gateway/src/index.ts:290-292` — 重复注册**直接抛异常**
2. **白名单是编译期常量**，由 tsdown 双 face 编译，运行期无法追加
3. **可行替代**：第三方插件在自己 Host 端 `ctx.on(...)`，然后通过**自己的 HTTP/WebSocket 路由**把卡片推给自己的前端 —— 不受白名单约束（白名单只管 DSH 的 Remote Events 通道）

## 5. `dsh-wechat` 双端同卡实现（可照抄）

### 5.1 监听（`WX/src/index.ts:151-175`）
```ts
context.on("approval/request", async (req, next) => {...}, { prepend: true });        // :151-159
context.on("user-questions/request", async (req, next) => {...}, { prepend: true });  // :160-175
```
- **必须 `prepend: true`**（`:145-150` 注释：「so we wrap next() (the GUI terminal answerer) instead of running after it」）——否则 GUI answerer 不调 `next()` 就永远轮不到
- **不带 scope tag** → 全局准入，能看到所有 session
- 错误策略：审批出错 → `next()` 回落 GUI；提问区分 `ASK_CANCELLED`/`ASK_ABORTED` 并 **rethrow**，其它错误才 `next()`

### 5.2 卡片渲染
审批（`adapter/approval-format.ts:36-74`）：
```
🔒 需要权限确认          （多张时 🔒 权限 ${i}/${total}）
工具: <toolName>
详情:
  <reason>
请回复其中一个：
  1. once   — 仅允许这一次
  2. reject — 拒绝这次调用
回复：1 或 2；关闭：/rq
```
- 单选卡用位置编号 1/2；多卡并存用 `P{n}=` 全局编号
- 长度上限 `MAX_CARD_LEN = 1800`（留微信 2000 字余量）

提问（`adapter/question-format.ts`）：单题 `formatSingle:106-116`、多题 `formatMulti:118-133`、选项 1-based 位置号 `appendOptions:135-146`。
回复语法四档优先级（`:11-17` + `parseQuestionReply:64-102`）：`Qn=` 形式 → `---` 位置分隔 → 单题整段即答案 → 多题无标记分段。

### 5.3 ★ 提交决定 = **resolve 一个本地 Promise**，不调 service
- 审批：`applyApprovalDecisions:2405-2428` → `respondApproval(entry, outcome):2417` → `settleWechat(outcome)`
- `settleWechat` 是 `answerApprovalRequest` 里创建 Promise 的 resolve（`:1818-1821`）
- 该 Promise 参与 `Promise.race([gui, wechatWrapped])`（`:1859`），**race 的返回值就是 waterfall listener 的返回值**（`:1875` `return winner.outcome`）
- 链路：微信文本 → 解析 → resolve Promise → race 结果 → 作为 listener return → `ApprovalService.decide()` 拿到的 outcome
- **全程没有调用 `ctx.approval` / `ctx.userQuestions`**

### 5.4 ★ `forkGuiCardSignal` —— 踩在未文档化细节上的捷径
`WX/src/bridge/bridge.ts:1763-1791`，注释说明动因：
> DSH 0.1.2 Web cards dismiss only when the waterfall `request.signal` aborts. The tool's own `exec.signal` must stay live so the turn can continue after a WeChat answer — so we replace `req.signal` with a fork for `next()` (GUI) and abort only that fork.

实现：`forkGuiCardSignal(req)` 就地替换 `req.signal` 为 fork；`abortGuiCard(guiAbort)` 结束时 abort fork。单向转发（original → fork）。

**原理**：`req.signal` 是 asker 传入的同一对象引用；waterfall 传的是**同一个 `req` 对象**，所以原地改写影响后续所有 listener → GUI 拿到 fork 版本，abort 就撤卡；**原始 turn signal 从未被 abort**。

⚠️【推测】**依赖两个非公开契约**：(a) `req` 在 waterfall 内共享可变，(b) GUI 用 `req.signal` 当展示寿命。**升级 DSH 后必须回归测试**「微信答→Web 卡消失」「GUI Stop→Web 卡消失」。

### 5.5 竞速 + 软超时
**竞速**：标准 `Promise.race`（`:1859`），输家必须 `.then(noop,noop)` 吞掉（`:1860-1861`）。
**后答者**：`respondApproval` 的 `if (entry.settled) return { accepted:false, reason:"not-pending" }`（`:2434`）→ 回「ℹ️ 该权限请求已在其他端处理」。
⚠️ **这是插件自己造的反馈**，DSH 层没有。

**软超时**（`cardTimeoutMs` 默认 30 分钟）：`setTimeout` **只从本地待办表移除 + 发提示，既不 resolve 也不 reject**（`:1832-1839`）→ race 仍挂着，GUI 仍活 → **不代用户决策**。
硬取消（`/rq`）才真改状态：审批 → `respondApproval(entry,"rejected")`；提问 → `cancelWechat(err)` 造 `ASK_CANCELLED`。

### 5.6 注册方式
- `inject: string[] = []`（零 `@deepseek-ai` 依赖），用**可选** `context.inject([...], cb)` 延迟绑定（`tools:97`、`commands:186`、`systemPrompt:223`）
- **无 `@Remote`、无 `ctx.remote.$on`**；客户端半边走**自己的 HTTP API**（`/wechat/api/*`）

### 5.7 `dsh-weixin` 有没有实现？—— **没有，且刻意规避**
`WX2/` 全目录**零审批/提问卡接入**。它往 agent system prompt 注入（`WX2/src/index.mjs:204-210`）：
> 「不要使用 ask_user_question 工具——它会在网页端阻塞等待回答，微信端无法响应会导致整轮卡住。」

→ **刻意选择不支持交互卡。**

## 6. 可复现评估

### 6.1 最小步骤（10 步，每步可独立验证）
1. 注册两个 prepend 监听器
2. 判断是否有本通道 peer（无则 `return next()`）
3. 自造卡片 id + 本地待办表
4. 渲染成 IM 文本并发送
5. 建两个 Promise 并 `Promise.race([next(), wechat])`
6. `forkGuiCardSignal(req)`
7. 软超时（只摘卡+提示，不 resolve/reject）
8. 入站回复解析 + 分发
9. 去重回执
10. dispose 时清空所有 waiter

### 6.2 DSH 提供 vs 必须自造
**DSH 提供**：两个 agent-scoped waterfall + 未 tag listener 全局准入；`req.agent`（完整 live Agent）、`req.signal`、`req.toolName`、`req.callId`、`req.reason`、`req.displayReason`；`next()` 委托 + fail-closed 兜底；**审批审计事件自动落盘（零成本）**；`intent:'plan-review'` 词汇；Web 端参照实现

**必须自造（8 项）**：
1. **卡片身份**（answerer 拿不到 id）
2. **竞速本身**（DSH 不 race）
3. **「已被其他端处理」回执**（DSH 没有）
4. **超时/卡片回收**（seam 无 timeout）
5. **文本渲染 + 回复语法**
6. **`fork` signal 撤 GUI 卡**
7. **IM 侧限流/消息窗口/重连去重**
8. **跨会话决策推送**（多 session 挂卡时的编号与路由）

### 6.3 工作量与风险
【推测】卡片逻辑约 **400–600 行 TS** + 等量测试。**格式/解析层（约 550 行）可几乎原样复用**，设计成本在竞速与状态机。

**风险（按严重度）**：
1. **`prepend: true` 是硬要求** —— 不加永远轮不到你，且**无任何报错**（最大静默失败点）
2. **`forkGuiCardSignal` 是未文档化依赖** —— 升级 DSH 必须回归
3. **等待期间 `next()` 一直挂着** —— turn 会一直不结束
4. **握手报错会静默吞卡**（`WX/tests/issue-2-card-silently-swallowed.test.ts` 就是回归测试）
5. **监听器必须不带 scope tag**
6. **`invariant` 会在开发模式抓你**
7. **提问卡不落 durable 事件** → **重启后未决提问卡随 turn 消失**，IM 侧会幽灵卡
8. **多插件并存冲突** —— 两个 IM 插件都 prepend，谁在前取决于加载顺序，**无仲裁机制**

### 6.4 一句话结论
**机制本身可复现且相当干净**：作为 **Host 进程内插件**，用两个 **agent-scoped waterfall 监听器**（`prepend: true`、不带 scope tag）就能拿到全部卡片请求，`return` 一个 outcome/answer 即完成裁决。**白名单、`@Remote`、`ctx.remote.$on`、`ctx.userQuestions.ask()`、`ctx.approval.request()` 在此路径上全都不需要。** 成本在**答案方要补齐 DSH 刻意不提供的 8 项**。

## 7. 对方案的决策含义

**Q24 的答案**：微信接提问卡**技术上是干净的**（两个监听器），但**成本不在"接"而在"补齐 DSH 不提供的 8 项"**。其中：

- **`forkGuiCardSignal` 是唯一踩在未文档化细节上的部分** —— 这是真实的技术债，不是不可克服
- **提问卡不落 durable 事件** → 重启后幽灵卡，必须有清理策略（监听 agent/session dispose）
- **等待期间 turn 不结束** → 与 Q20 的「出站投递」耦合：需要 typing keepalive 维持观感

**建议**：v1 做**审批卡**（有 durable 审计、语义清晰），提问卡作为 v2。理由：
- 审批卡的 `approval/asked` + `approval/decided` **自动落盘**，重启可恢复
- 提问卡**不落盘**，重启即丢，需要额外的幽灵卡清理逻辑
- 两者共用同一套机制，先做一个的边际成本远低于同时做
