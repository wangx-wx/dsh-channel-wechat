# 侦察报告 09：长连接与推送机制（Q20 最终）

> 来源：子任务 07d50433（只读核查，两仓库）
> 结论：**微信侧不能**（只有长轮询）；**DSH 的 Web 实时流第三方插件无法复用**；**微信能主动推送，但收件人须历史上与 bot 有过会话**

## 理解 A：微信侧不能升级为长连接

### A1 收消息只有 getUpdates 长轮询
- **文档明说**：`docs/protocol_zh_CN.md:23-25`；`:152-162` 穷举全部 **7 个** endpoint，**无 WebSocket/SSE/回调**
- **代码事实**：全仓 endpoint 字符串仅 9 处（`api.ts:460,495,585,604,624,640,655`；`login-qr.ts:101,135`），全走 `fetch()`
- 全仓 grep `websocket|ws://|wss://|EventSource|text/event-stream|SSE|callback_url|webhook|push` **零命中**
  - ⚠️ 唯一 "webhook" 命中是 `channel.ts:497` 日志文案 `starting weixin webhook` —— **误导，不是 webhook**
- **未找到证据**：无回调 URL 注册字段、无设备注册 endpoint、无服务端主动推送

### A1a 长轮询语义
- `DEFAULT_LONG_POLL_TIMEOUT_MS = 35_000`（`api.ts:211`），可被服务端 `longpolling_timeout_ms` 覆盖（`monitor.ts:107-110`）
- 客户端到点自 abort，AbortError 当**正常空返回**（`api.ts:475-484`）
- ⚠️ **返回值无法区分「服务端超时」与「客户端自 abort」**（都是 `ret:0,msgs:[]`）
- ⚠️ `WeixinApiOptions.longPollTimeoutMs` 是**死字段**（`api.ts:28-29`，全仓仅此一处引用）→ 实际永远 35s

### A1b notifyStart/notifyStop **不建立订阅**
纯 fire-and-forget POST（`api.ts:637-662`），语义为「通知后端客户端启动/停止」，无订阅语义。

### A1c 串行，单账号同时恰 1 个 getUpdates 在飞
`monitor.ts:89-208` 单 `while` 循环，`await getUpdates` → `await processOneMessage`（`:172`）→ **纯串行**。
grep `maxConcurrent|concurrent|Promise.all|parallel` 零命中。
副作用：**消息处理慢会推迟下一次轮询**。cursor 落盘**无锁**（推论：多进程同账号会互相覆盖）。

**→ 理解 A 答案：不能。客户端无法自行把 iLink 升级成长连接。**

## 理解 B：DSH 侧事件流

### B3(a) `ctx.on('session/event')` —— durable，同步 emit，不 await
- post-commit、fire-and-forget；listener 快照在 log push 前解析、回调在 push 后跑（`session/src/index.ts:66-77,759-764`）
- observer 异常 log & contained，每 listener 单独 try/catch（`:403-419`）
- durable 但**不补发**：seed events 不发（`:476`）；错过窗口只能靠 `sessionQuery.observeSession` 读回
- scope-filtered，跨全部 session 需 `{ global: true }`

### B3(b) `ctx.on('agent/assistant-stream')` —— process-local，**chunk 会丢**
- JSDoc「Process-local … **Chunk frames are transient**」（`agent/src/runtime-types.ts:355-363`）
- **无订阅者即丢弃，无持久化/重放/baseline**（`agent/src/dispatch.ts:117-130`）
- ⚠️ 唯一补救是 session-controller 私有（`api/session-controller/src/assistant-stream.ts`）—— **普通插件拿不到**

### B3(c) `ctx.jobs.events.subscribe` —— 同步、不 await、粒度=job
- JSDoc「**never awaited**」（`jobs/src/types.ts:239-240`）
- ⚠️ `output` 事件只带 id+total，**不推 payload**（`:195-197`）→ 要看输出得自己 readAt
- effect-scoped，卸载自动注销；进程内

### B3(d) AsyncIterable / 流 / SSE
1. Host 远程流 → `/api/remote.mux`（`api/gateway/src/stream-protocol.ts:7`）
2. **session-controller `follow()` = durable + live 合一的官方流**（`history.ts:120-240`），带 **gap 检测**（`:222-228` seq 跳号抛错）
3. `ctx.remote.$stream()` 是**客户端侧**
4. ⚠️ **Host 事件转发只有 1 个 source 席位**（`gateway/src/index.ts:285-291`，第二次注册 throw）
5. SSE 能力上允许，但 DSH **无任何 SSE 事件生产者**

### B5 ★ Web 实时通道不能被第三方插件复用
- 走 **WebSocket**（`stream-protocol.ts:7` `REMOTE_STREAM_MUX_PATH='/api/remote.mux'`），**不是 SSE**
- 升级前强制鉴权（浏览器 cookie，`gateway/src/index.ts:252-257`）
- **三条阻断理由**：
  1. **单事件源席位**——第二次注册 throw
  2. **静态 allowlist**——`api/remotes/src/remote-events.ts:19-45` 的 26 项里**没有** `agent/assistant-stream` / `session/event`
  3. **web-app 专用**——`api-remotes`、`connection`、`webServer` 都只在 web-app bundle；headless「mounts no Host, HTTP server, Web runtime」

→ **微信外推应走进程内 `ctx.on` / `ctx.typertGateway.wireStream.open(...)`**（后者是公开 API，`peer` 可为 undefined，先例 `experimental/webworker-runtime/src/worker-host.ts:279`）。`/api/remote.mux` 与 cookie 认证对微信侧**零价值**。

### B4 「一有输出就推微信」的挂载点
- ① 只推已提交 → `session/event` 过滤 `assistant/message`（稳，非逐字）
- ② 要逐 chunk → `assistant-stream` 的 `frame.type==='chunk'`（**要自己合帧、处理 revision+index+attempt 重试**）
- 官方先例：`bundle/headless/src/index.ts:121` 逐块流 reasoning

**边界**：
1. **微信侧无补投/重放** → 必须自建队列+重试+幂等（`client_id`）
2. `-14` → 1 小时账号暂停，期间出站 throw
3. **插件重载**：`ctx.on` disposer 随 fiber 撤销 → 异步发送要 drain
4. **进程重启**：`session/event` 可按 seq 补；**`assistant-stream` 无重放** → 跨重启不丢以 session/event 为准
5. 别抢占 getUpdates 节奏

## 附加：微信能否主动推送（不经用户先发）

**结论：能，但收件人必须历史上与 bot 有过会话。**

- 唯一出站 = `POST /ilink/bot/sendmessage`，带 `to_user_id` + `context_token`（`send.ts:69-79`）
- **`context_token` 仅来自入站消息**（`inbound.ts:18-22` 注释：「issued per-message … must be echoed verbatim」）；落盘 + 重启恢复（`channel.ts:496`）
- 主动路径存在：`channel.ts:76-116 resolveOutboundAccountId`（注释明说为 cron delivery 而设）
- **无历史会话直接 throw**（`channel.ts:110-115`：「ensure the recipient has recently messaged the bot」）

**限制**：
1. token **per-message**，插件每 user 只留最近一个（`inbound.ts:101-105`）
2. ⚠️ **无 token 时继续发但未经证实**——官方文档 `protocol_zh_CN.md:248` 明说「这不能证明服务端一定接受该请求」← **最关键不确定点，需实测**
3. `-14` → 1 小时全局暂停，出站 throw
4. 收件人须 `@im.wechat`
5. 多账号歧义时 throw，需显式 accountId

**文档明说**：官方文档**从未**把「主动推送」列为能力，它是 outbound + cron/announce 投递的自然结果（属代码事实）。

## 对方案的影响

1. **长轮询是唯一形态**，「长连接」在微信侧不成立；但在 DSH 侧可用 `ctx.on` 做实时外推。
2. **★ 推翻一个说法**：我曾说「Web 的 remote.mux 也许能复用」——**不能**（单席位 + 静态 allowlist + web-only）。微信外推必须走进程内 `ctx.on`。
3. **必须自建出站队列**（微信侧无补投/重放），并用 `client_id` 做幂等。
4. **主动推送的前置条件是「用户先和 bot 说过话」** —— 这是产品级限制，必须在 README 写明。
5. **逐字流式推送的代价高**（要自己合帧、处理 revision/index/attempt 重试），且 **chunk 跨重启会丢**。→ 建议以 `session/event` 的 `assistant/message` 为准，不做逐字。
