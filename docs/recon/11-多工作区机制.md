# 侦察报告 11：DSH 多工作区机制（Q19 答复）

> 来源：子任务 672a4f00（只读调查，DSH @ 4878cda / 0.2.0-rc.1）

## ★ 核心结论：GUI 的「切换工作区」= 切换当前 Session

**不存在**「切换当前工作区」这种服务调用。每一次都是**切到某个 Session**。

`WorkspaceView` 就是 `Workspace` 实体的投影（`api/workspace-controller/src/feed.ts:23-32,74`），侧栏按 view 分组渲染（`client/ui-workspace/src/client/tree.ts:337-375`）。

**「当前工作区」在 Host 侧不存在**：
- 持久化的只有**当前 SessionId**：`navigation.ts:130-132`（`dsh.sessions.current`，落 localStorage）
- 「当前工作区」是**客户端派生值**：`navigation.ts:226-231` 由当前 sessionId 反查 `workspace.items.find(item => item.sessionIds.includes(current))`
- 另有纯 UI 展示偏好 `dsh.workspace.view.v5`（分组/排序/折叠），**不是**「当前工作区」

## 切换链路

| 动作 | 链路 |

## ★ 切换是「复用空白会话或新建」，不恢复旧对话

`navigation.ts:179-189`：遍历会话列表，**仅当** `summary.blank && summary.cwd === workspace.path && workspace.sessionIds.includes(id) && 未归档` 时 `reuseBlank`；否则新建。

> 「切回某工作区」= 复用它的**空白会话**或新建一个空白会话；**要看旧对话必须点会话行**。

重载恢复：`navigation.ts:318-347`（saved.sessionId 为 blank 且 cwd 匹配才 reuseBlank）。并发去重靠 `connecting` map。

## cwd 来源

`api/session-controller/src/commands.ts:119`：
```ts
const cwd = workspace?.path ?? request.cwd ?? this.defaultCwd
```
`defaultCwd` 是**进程 cwd**（`src/index.ts:139` `process.cwd()`）。
`SessionCreateRequest{workspaceId?, cwd?, sessionId?, agentPreset?}`，**禁止二者同时给**（`:106-108`）。
写入：`agent.ts:481` mkdir recursive → `:486-494` `ctx.agents.create({meta:{cwd}})` → `core/session/src/index.ts:1053` 一次写入 SessionHeader，**全仓无 setCwd**。

**外部插件使用的前置条件**：
1. **该部署必须挂载本包**：`static inject = ['storageDomain','sessionPersistence']`；**实际只有 web-app bundle 挂它**（`bundle/web-app/cordis.patch.yml:91-92`）—— **base / headless / sdk / acp 都没挂**
2. `create` 要求目录已存在且是目录（只有 `initializeDefault` 会替调用方创建）
3. `attachSession` 需要 session 已有 header，且 **header.cwd realpath 后必须等于 workspace.path**
4. 调用方包需声明 peer `@deepseek-ai/dsh-workspace`，并在 registry 之后加载

## ★ Q6 外部通道复刻「多工作区+切换」

**可以复刻到**：「多目录分组 + 每目录建/复用空白会话」
**不可能复刻**：「把已有会话迁到别的目录」——cwd 一旦写入即终局，`attach` 要求 cwd 相等

**与 GUI 的行为差异**（外部通道需自己实现，否则每次切换都新建空白会话）：
- GUI 会复用该 workspace 的空白会话
- GUI 会迁移输入草稿/附件（`apply.ts:330-350`）
- GUI 写 `dsh.sessions.current` 以便刷新恢复

**只挂 `meta.cwd` 不挂 `workspaceRegistry` 的后果**：会话仍能在 GUI 里看到，但落在**「未分组」桶**（`list.ts:138` 只过滤 `cwd===undefined`；`tree.ts:344-375`）。失去：
- 按目录分组 / 工作区选择器标题
- workspace 级 pin/归档页面位置
- 按 cwd 共享的 Electron 浏览存储分区（`ui-sidebar-browser/.../workspace.ts:32` 返回 `cwd:${path}`，否则 `session:${id}`）

## Q7 官方「按目录隔离会话」实践

| 组件 | 做法 |
|---|---|
| **webhook**（最接近的官方外部通道） | 强制 `workspacePath` 绝对路径；`workspaceRegistry.create(path)` → 写入 `SessionHeader.cwd` → 先 attach 再权限/标题/prompt，失败回滚（`webhook/src/session.ts:39-44,129-141,129-174`） |
| **headless** | `cwd = fs.processPath(await fs.resolve('.'))`；`--session-id` 认领要求记录 cwd 相同，否则拒绝 |
| **ACP** | `session/new` 带 `params.cwd`；`session/resume` 校验 `persisted.cwd` 与 `params.cwd` **sameDirectory**，不匹配抛 `invalidParams`；`listSessions` 支持按 cwd 过滤 ← **最明确的「按目录隔离会话」实现** |
| **SDK** | cwd 是启动参数/握手字段；`--workspace/cwd` 做隔离实践 |
| 持久化层 | 本身就按 cwd 分目录（`session-persistence-jsonl/src/format.ts:222-274`，无 cwd 落 `_no-cwd`） |

## 一句话结论

> GUI 的「多个工作区 + 切换」= 多个 workspaceRegistry 记录 + 每个记录一个会话列表；**「切换」在语义上等于切换当前 Session**（新工作区只复用空白会话或新建），客户端只持久化 `dsh.sessions.current` 这一个 sessionId。

## 对方案的影响

1. **Q19 要重新表述**：不能说「支持切换工作区」——应该说「支持多工作目录，每个目录对应独立会话组」。语义上等价，但实现上必须**新建/复用空白会话**，无法迁移。
2. **`workspaceRegistry` 只在 web-app 挂载** → 若我们的插件要在 headless profile 跑，**必须先挂 `dsh-workspace`**，否则 `ctx.workspaceRegistry` 不存在。这是一个部署依赖，必须写进 README。
3. **ACP 的实现是最佳参照**（`session/new` 带 cwd、`resume` 校验 sameDirectory、`listSessions` 按 cwd 过滤）—— 与我们要做的「微信侧多目录」几乎同构。
4. **不挂 workspace 也能用**，代价是 GUI 里落「未分组」桶——对单用户场景可接受，但用户明确要求对齐 GUI 体验，所以应挂。
