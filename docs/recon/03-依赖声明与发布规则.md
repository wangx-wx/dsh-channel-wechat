## 3. out-of-tree 插件包结构（官方教程 `docs/user/develop/basic/publish.md`）

```
hello-plugin/
├─ package.json       # 声明 dsh.bundle
├─ cordis.patch.yml   # 本 bundle 的配置层
└─ index.js           # patch 行引用的插件模块
```

**(a) `dsh.bundle` 清单字段**

```json
{ "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } }
```

- `patch` 可为 `string | string[]`，数组按序作为**同一层**应用（`publish.md:64`；`packages/util/package-manifest/src/types.ts:69-71`）
- 不声明 `dsh.bundle` 的包仍可安装，但只打警告且**不激活层**（`plugin-manager/src/operations.ts:100-103`）
- 可选 `dsh.manifestVersion`、`engines.dsh`、`dsh.client`（均不强制）

**(b) `cordis.patch.yml`**：顶层 YAML 数组，用**包名**引用自身模块

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin
    - id: hello-search          # 子路径
      name: '@fixture/bundle/search'
```

参考：`apps/web/tests/fixtures/plugins/fixture-bundle/cordis.patch.yml:1-8`、`packages/experimental/schedule-bundle/cordis.patch.yml`
**覆盖宿主已有行时必须重述整行 config**（`publish.md:131`）

**(c) `prepare` 脚本**：Git 安装拿到的是**源码不是构建产物**，作者需提供自包含 `prepare`（pnpm 在 git 安装后运行）从 `src/` 构建发布入口，**不得假设旁边有 monorepo**（`publish.md:169`）。npm / tarball 路线不需要。

**(d) pnpm `allowBuilds`**：pnpm ≥10 在显式允许前拒绝运行 git 依赖的 `prepare`，首次 add 会失败。用户需把 pnpm 打印的键抄进 profile 的 `pnpm-workspace.yaml`：

```yaml
allowBuilds:
  dsh-hello-plugin: true
```

**安全含义**：这是「允许安装时以宿主用户权限执行代码」，建议**钉 commit sha**（`publish.md:179`）。

**(e) `files` 字段**：至少含入口 js + `cordis.patch.yml`。要展示 metadata/图标还需含 `locale/*.json` 与 `icon.svg`，并在 exports 暴露 `./package.json`、`./locale/*.json`。仓库内发布包**不得含** `src/`、`*.d.ts.map`、`*.js.map`（`scripts/publication-payload.ts`）。

## 4. GitHub 直装 vs npm 发布

| | GitHub 直装 | npm / tarball |
|---|---|---|
| 拿到的是 | **源码**，不跑 build | 预构建产物 |
| 作者需提供 | 自包含 `prepare` | 无 |
| 用户需操作 | `allowBuilds` 授权 + 重跑 add + 建议钉 sha | 无 |
| 其他 | 先 `git ls-remote` 预检（默认超时 5000ms） | — |

两者都受版本兼容检查约束；git/tarball spec 在**装完后**判定，失败会回滚 manifest + lockfile（`plugin-manager/README.md:52`）。

## 6. `verify-application-entrypoints` 门禁规则

实现：`scripts/verify-application-entrypoints.ts`（203 行），三条规则：

| 规则 | 内容 |
|---|---|
| (1) `manifestBinViolations`（:100-118） | 只 glob `apps/*/package.json` 与 `packages/*/*/package.json`。出现 `bin` 且不在白名单（仅 `apps/cli` → `dsh`、`webworker-packer`）即失败，报错「package bin bypasses the dsh launcher」 |
| (2) `executableSourceViolations`（:119-131） | 扫描根 `*.ts/js/mjs/cjs`、`apps/**`、`packages/**`、`python/sdk-runtime/*.mjs`；以 `#!` 开头且不在白名单即失败 |
| (3) `rootLauncherViolations`（:140-175） | 根 `package.json` scripts 的 `demo:*` / `start:*` 必须指向 `apps/cli/src/bin.ts` |

**意图**（`.agents/notes/.../2026-08-22-single-dsh-application-launcher.md:55`）：
> 「Vendor CLIs、build-only、test-only 可执行文件、**直接 in-process 挂载插件**、私有 WebWorker 预览都在 application-launch inventory 之外；包级 app bin 或绕过 dsh 的 root demo 不是被接受的扩展点。」

即：**允许 in-process 挂载插件，禁止新增独立 Node 应用入口。**

**out-of-tree 插件是否受约束**

| 场景 | 结论 |
|---|---|
| 包在仓库外 | **不受约束**（门禁只 glob 仓库内，且须从仓库根运行） |
| 放进仓库树内 | shebang 源文件落在 `apps/**` 或 `packages/**` 会被规则 (2) 检查；`bin` 仅在 `apps/<x>/` 与 `packages/<g>/<p>` 两个深度被规则 (1) 检查 |
| 放在仓库根（教程做法） | 根级 `package.json` 不参与规则 (1)；嵌套的 `index.js` 不在规则 (2) 扫描范围 |

> ⚠️ 另注：`verify-package-dependencies.ts` + `package-dependency-policy.ts` **也只覆盖 workspace 包**（`:22-27`），明确不选 `packages/experimental`。
> **因此 out-of-tree 插件的 peer/dep 分区没有任何仓库门禁保护——只能靠作者自律 + 本报告第 2 节的规则。**

## 7. 对本项目的影响（关键）

1. **`@deepseek-ai/*` 可正常作为 peer/dev 依赖**，用户体验接近普通 npm 包。
2. **★ 版本区间必须含预发布**：peer 写 `"^0.2.0-rc.1"` 而非 `"^0.2.0"`，否则**安装直接被拒**。这是最容易踩死的一步。
3. **不要用 `latest`**：官方包的 latest tag 落后于运行版本。
4. **发布路线选择影响用户体验**：
   - npm 发布 → 用户零额外操作（**推荐**）
   - GitHub 直装 → 用户必须做 `allowBuilds` 授权（等于允许安装时执行代码），且要 `prepare` 脚本自包含
5. **我们可以照抄官方模板**：`templates/decoration/` 是最正规的起点。
6. **门禁不约束 out-of-tree 包**，但我们仍应遵守同一套规则（尤其「不做 bin」），以保持一致并便于未来进仓库。
7. **没有现成的 out-of-tree 发布实例可参考** —— 我们要自己趟通这条路，这部分应列入 P0/P4 的验证内容。
