# 侦察报告 02：插件命令行入口与二维码登录机制

> 来源：子任务 5e16a11a（只读调查，DSH 仓库）
> 结论：**方案 §5.4 的未决问题已解决** —— `dsh wechat login` 可用，`login` 会作为 app-arg 传给插件。

## 1. 参数解析规则（已实测确认）

**`dsh wechat login` → profile = `wechat`，app-args = `["login"]`。`login` 不会被吃掉。**

三重证据：

| 证据 | 位置 |
|---|---|
| 简写展开：首 token 非 `-` 且非 `plugin` → 重写为 `['--profile', ...argv]` | `apps/cli/src/args.ts:200-204` |
| 启动器只认自己的 flag：`allowUnknownOption()` + `passThroughOptions()` + `enablePositionalOptions()` | `apps/cli/src/args.ts:150-172`；commander `command.js:1876-1906, 1921-1924, 1562-1568` |
| **运行时实测**（直接 import args.ts） | `["wechat","login"]` → `{mode:"profile", profile:"wechat", args:["login"]}` |

单测对应：`apps/cli/tests/args.spec.ts:43-44`、`:35-47`

**边界规则（会咬人的地方）**

- `dsh login wechat` → profile 是 `login`，`wechat` 变成 app-arg（简写只认第一个 token）
- `wechat` **不是内置模板**（内置仅 web/headless/sdk/sdk-minimal/acp，`packages/boot/app-boot/src/profile.ts:179-195`）；profile 目录必须先存在，否则抛 `profile ... does not exist`
- `dsh wechat --help` → 应用自己的 help；`dsh wechat -- --help` → 同样（启动器吃掉一个 `--`）
- app-args 经 `ctx.cmdlineArgs` 原样传入：`apps/cli/src/profile-boot.ts:307-311`

## 2. 插件接收 app-args 的最小骨架

官方机制为 `@deepseek-ai/dsh-cmdline`：插件 inject `cmdlineArgs`，自带 commander program，调 `parseCmdline(ctx, program)`，在 action 里 `ctx.provide(服务名, 值)`。

第一方样板：`packages/bundle/web-app/src/startup.ts:14,17,70-88`
已验证 fixture：`apps/cli/tests/built-bin.e2e.ts:249-260`

```ts
import { Command } from 'commander'
import type { Context } from '@deepseek-ai/cordis'
import { parseCmdline } from '@deepseek-ai/dsh-cmdline'

export const name = 'wechat-startup'
export const inject = ['cmdlineArgs']
export const WECHAT_STARTUP_SERVICE = 'wechatStartup'

export function apply(ctx: Context): void {
  const program = new Command()
    .name('dsh --profile wechat')
    .argument('[action]', 'login to print the QR code')
    .option('--json', 'machine-readable output')

  program.action(() => {
    const action = program.args[0]
    if (action !== undefined && action !== 'login') {
      program.error(`error: unknown action ${JSON.stringify(action)}`)
    }
    ctx.provide(WECHAT_STARTUP_SERVICE, { action, json: program.opts().json === true })
  })

  parseCmdline(ctx, program)   // 必须在 action 之后
}
```

配套 patch（**行本身不写 `inject`**，插件导出即可；对比 `packages/bundle/web-app/cordis.patch.yml:159-162`）：

```yaml
- insert:
    - id: wechat-startup
      name: '@acme/dsh-wechat/startup'
    - id: wechat-login
      name: '@acme/dsh-wechat/login'
      inject: [wechatStartup]
      config:
        action: !!js ctx.wechatStartup.action ?? 'none'
```

**契约要点**

- `parseCmdline` 通过 `ctx.get('cmdlineArgs')` / `ctx.get('appExit')` 取值（**不是属性代理**）：`packages/boot/cmdline/src/index.ts:165-186`
- 程序**必须至少有一个 command 声明 action**，否则抛错：同上 `:173-175, 199-202`
- action 必须**先校验、后发布**：`program.error()` 之前执行的语句已经生效（`:157-158`）
- `program.error()` / `--help` 会走 `ctx.appExit` 退出，**不发布服务**，所以依赖它的行不会激活
- 不可变快照：`:27-33`、`:84-89`（`Object.freeze`）

**包与导入路径**

| 用途 | 包名 | 导入 |
|---|---|---|
| 命令行 seam | `@deepseek-ai/dsh-cmdline` | `parseCmdline, provideCmdline, exitOnStdinEnd` |
| 参数解析器 | `commander`（`^15.0.0`） | `import { Command } from 'commander'` |

**out-of-tree 可解析性**：`@deepseek-ai/dsh-cmdline` 与 `commander` 会进入安装级解析表（apps/cli 声明了它们；该表对 dependencies **和 peerDependencies** 做 BFS，`packages/boot/app-boot/src/profile.ts:386-398`）。e2e 注释明确 out-of-tree bundle 正是这样解析到它们（`apps/cli/tests/built-bin.e2e.ts:234-240`）。

## 3. 二维码呈现方式（按推荐度排序）

**(a) 终端 ASCII 二维码 + stdout —— 推荐**

理由：最贴合 `dsh wechat login` 的交互模型，此时终端就在用户面前。有第一方先例：`packages/bundle/web-app/src/index.ts:270-279` 在 tree settle 后 `console.log` 打印 URL。

⚠️ **仓库内无第一方终端二维码先例**，也无包直接依赖 `qrcode`。需自带编码器或把依赖装进 profile（`qrcode-terminal` 是候选，见侦察报告 01）。

**(b) 注册 HTTP 路由渲染二维码页，并打印 URL**
`ctx.webServer.register({ kind, path, handler })`：`packages/host/webserver/src/index.ts:161-173`。浏览器扫码比终端 ASCII 好扫。注意 `/api` 鉴权边界。

**(c) 自带 client 半边做设置卡片/Plugins 页面**
`docs/cookbook/adding-a-settings-card.md:56-72`、`packages/client/ui-settings-shell/src/client/index.ts:50-52`。最重，体验最好，可显示登录状态。

## 4. 重要否定结论：没有兜底机制

若插件不解析 `login`，**`login` 被静默忽略，profile 照常启动，什么也不会发生**。

明证：`packages/boot/cmdline/README.zh.md:70` —— 「启动器不会决定谁是命令行的所有者：**没有读取方的应用会忽略自己的参数**」。

其他通道均不可用作启动期登录入口：

| 通道 | 结论 |
|---|---|
| 启动器级 `login` 命令/flag | **不存在**（`apps/cli/src/args.ts:90-100, 151-172`）；`dsh login` 只会把 `login` 当 profile 名 |
| Web UI 通用授权入口 | **不存在**。`ctx.authorization` **无 `@Remote`**；唯一生产调用方 interaction 是空实现（`packages/credentials/deepseek-account-platform/src/index.ts:426-428`） |
| `/` 命令注册表 | 第一方只有 plan/compact/feedback/goal/session-log-export/permission-presets，**无登录类命令** |
| `ctx.userQuestions.ask()` | 运行期、**面向存活 agent** 的通道；启动插件无 agent，不适用（`packages/interaction/user-questions/src/index.ts:86-100`） |
| headless 读 stdin | 有先例（`packages/bundle/headless/src/runner-internals.ts:13-20`），但**无第一方交互式提问先例**（`readline` 仅出现在测试/脚本中） |

**结论**：登录入口必须由插件自己提供，且方案已确认可行的方式就是 §2 的 cmdline provider。

**新增约束**：登录行必须遵循「provider 先发布服务、consumer 行用 `!!js` 读取」的两段式结构，不能在一个插件里直接读参数后立即执行——因为 `parseCmdline` 的 action 与服务发布是两个阶段，且 help/错误路径会 `appExit`。
