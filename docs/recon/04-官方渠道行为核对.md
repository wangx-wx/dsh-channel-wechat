# 侦察报告 04：官方微信渠道行为核对

> 来源：子任务 cd759665（只读审计 openclaw-weixin v2.4.9 @ 24de5c9）
> 用途：回答 grilling 第一轮中被转为事实问题的 Q5 / Q6 / Q9 / Q10

## 1. 回复投递（答 Q5）

**结论：整段投递，不是流式分块。**

- 插件声明 `capabilities.blockStreaming: true`、`textChunkLimit: 4000`、合并策略 `{minChars:200, idleMs:3000}`（`channel.ts:229-239,267-269`）
- 但真正回复路径**显式关闭**：`replyOptions: { disableBlockStreaming: true }`（`process-message.ts:540-545`）
- 每次 deliver：整串过 `StreamingMarkdownFilter`（markdown 清洗，**非分块**）→ 一次 HTTP 发送（`process-message.ts:369-373,444-477`）
- **本仓库无任何文本分块逻辑**。`textChunkLimit: 4000` 是**声明给宿主的**，实际是否切分由 OpenClaw 宿主决定 **[宿主侧不可见]**
- 文本+媒体：拆成两条独立请求，各有独立 `client_id`（`send.ts:192-264`；协议文档 `protocol.md:248` 明载）
- **插件侧无发送节流**，唯一串行化是工具进度消息的 promise 链 `sendChain`（`reply-progress-sender.ts:58-74`）

**typing 保活**：ticket 来自 `getConfig`，按用户缓存 TTL 随机 24h、失败指数退避至 1h（`config-cache.ts:8-10,31-78`）；`keepaliveIntervalMs: 5000`；**无 ticket 时 start/stop 都是 no-op**（`process-message.ts:342,354`）

## 2. 并发模型（答 Q6）

- **串行 await，且阻塞长轮询**。`for (const full of list) { await processOneMessage(...) }`（`monitor.ts:157-183`，await 在 172）。整个 AI turn 跑完才回到 `while` 顶部重新 `getUpdates`
- 后果：处理长任务期间**不再发起 getUpdates**，新消息由服务端积压
- **没有队列、没有 pending 表、没有消息去重**。唯一游标是 `get_updates_buf`，每账号持久化到 `{accountId}.sync.json`。崩溃在批处理中途**会重放整批**（无逐条 ack）
- **用户不能打断/取消正在进行的任务**：全仓无 `/stop`，无 turn 级 abort 传播到 dispatch。唯一取消是 gateway 停止/热重载时取消 in-flight long-poll，且该 signal **没有传进** `dispatchReplyFromConfig`

## 3. 斜杠命令

**插件自己实现的只有 2 个**（`slash-commands.ts:86-97`）：

| 命令 | 作用 |
|---|---|
| `/echo <message>` | 直接回复，不走 AI；附通道耗时统计 |
| `/toggle-debug` | 翻转该账号 debug 模式并持久化 |

- 分发：仅当**第一个 TEXT item** 以 `/` 开头才尝试；按第一个空格切分，command 转小写（`process-message.ts:61-70,93-113`）
- 未识别 → `handled:false` → **fallthrough 到正常 AI 管道**（即未知斜杠命令会被当普通消息发给模型）
- **不是转发给框架 commands 注册表**。框架 `channelRuntime.commands` 仅用于**鉴权**（`process-message.ts:189-207`）；宿主是否在 dispatch 内部再执行注册命令 **[宿主侧不可见]**
- 授权策略硬编码 `dmPolicy: "pairing"`、`isGroup: false`

## 4. 消息类型（答 Q9）

`MessageItemType`：TEXT=1, IMAGE=2, VOICE=3, FILE=4, VIDEO=5, TOOL_CALL_START=11, TOOL_CALL_RESULT=12

**入站**
| 类型 | 处理 |
|---|---|
| 文本 | 取第一个 TEXT item 作 Body |
| 图片 | CDN 下载 + AES-128-ECB 解密；密钥优先 `image_item.aeskey`，其次 `media.aes_key`，**都无则按明文下载** |
| 语音 | **转写优先**：有 `voice_item.text` 则直接作 Body 且**不下载媒体**；否则下载 SILK→WAV；转码失败存原始 `.silk` |
| 文件 | 下载解密，MIME 由后缀猜 |
| 视频 | 下载解密，固定 `video/mp4` |

- 优先级 **IMAGE > VIDEO > FILE > VOICE，只处理第一个**（`process-message.ts:127-146`）
- 引用内媒体兜底：主 item_list 无媒体时取 `ref_msg.message_item` 的媒体（`process-message.ts:147-170`）
- 媒体上限 **100 MiB**（`media-download.ts:9`）

**出站**：文本、图片、视频、文件。上传走 `getUploadUrl` → AES-128-ECB 加密 → POST CDN → 取 `x-encrypted-param`，重试 3 次、4xx 立即失败

**明确未实现**
| 项 | 证据 |
|---|---|
| 缩略图上传 | 永远 `no_need_thumb: true`（`upload.ts:91`；`protocol.md:299` 承认） |
| **出站语音** | `media_type:4` 只在类型里，发送管线只选 image/video/file（`protocol.md:299`） |
| **群聊** | `capabilities.chatTypes: ["direct"]`；`group_id` 全仓无读取点（`channel.ts:230`、`types.ts:203`） |
| `sync_buf` | 标 deprecated，不读不写 |

**type 11/12 是给用户看的，不是给模型看的**：
- 仅出站方向，工具 start/end 各发一条微信消息，metadata 只带 `tool_name`/`tool_call_id`/`status`；**入参/结果正文被显式丢弃**（测试断言 `summary`/`progressText` 不应发送）
- 入站路径**从不解析** 11/12
- 开关 `replyProgressMessages` 默认 true

## 5. 主动推送（答 Q10）

**能，但走宿主投递接口，不是插件自建定时器。**

- `outbound.deliveryMode: "direct"` + `sendText`/`sendMedia`（`channel.ts:267-381`）就是宿主 cron/announce 投递的落点
- `resolveOutboundAccountId`（注释写明 "cron delivery without explicit accountId"，`channel.ts:78-116`）：
  1. 账号数 0 → 抛错提示 login
  2. 账号数 1 → 直接用
  3. 多账号 → 用**内存 contextToken 表**反查；多命中抛 ambiguous，零命中抛错
- **关键约束：收件人必须曾给 bot 发过消息**（或用磁盘 `{accountId}.context-tokens.json` 恢复过）
- `agentPrompt.messageToolHints` 教模型怎么建 cron：须设 `delivery.to` 与 `delivery.accountId`，示例 `{ mode:'announce', channel:'openclaw-weixin', to, accountId }`（`channel.ts:251`）
  → **宿主支持定时投递到微信由此确认**；cron 本身在宿主体内 **[宿主侧不可见]**
- 插件内唯一定时器是 quote-store GC（1 小时），与投递无关

**`notifyStart`/`notifyStop` 语义**：向微信后端声明该 bot 客户端**上线/下线**（body 仅 `base_info`），用于服务端对齐在线状态。调用点：`startAccount` 起来后调 notifyStart（失败仅 warn）、`stopAccount` 调 notifyStop。

**中途进度通知**
- `reply-progress-sender.ts`：工具调用 start/result 两条进度消息，串行，绑定 `runId`
- `error-notice.ts`：**投递失败时**给用户发纯文本错误提示（fire-and-forget，永不抛）。按错误分三类：媒体下载失败/上传失败/其他发送失败

## 6. 会话/对端模型

- **群聊未实现**：`chatTypes: ["direct"]`；鉴权硬编码 `isGroup: false`
- **单聊对端 = `from_user_id`**：`To = From = OriginatingTo = from_user_id`，`ChatType: "direct"`；入站 `to_user_id` 被忽略
- **路由**：`resolveAgentRoute({channel, accountId, peer:{kind:'direct', id:ctx.To}})`，把 `route.sessionKey` 写回 `ctx.SessionKey`
- **contextToken 维护**：每条入站消息的 `context_token` 按 `${accountId}:${from_user_id}` 存内存 + 落盘；**出站必须原样回带**
- **引用（quote-store/partial-quote）会影响模型看到的输入**：
  - 双向入缓存（SQLite，`node:sqlite`，WAL）
  - 解析后写 `ctx.ReplyToBody`/`ReplyToQuoteText`；命中媒体则 **append 进 `ctx.MediaPaths`** 并追加 prompt 提示
  - 未命中给 `"[引用消息内容未缓存]"`；过期给 `"[引用的图片/视频/语音/附件已过期(: name)]"`
  - 缓存策略：默认 30 天/账号 10000 条；媒体 7 天/256 MiB/单文件 25 MiB
  - 降级：`node:sqlite` 不可用或禁用 → 直接关闭，**无内存回落**

## 7. 复刻最容易踩的 5 个点

1. 回复路径 `disableBlockStreaming: true` —— 声明了 blockStreaming 但实际整段投递
2. 串行 await 阻塞 long-poll，无队列/无去重，唯一游标是 `get_updates_buf`
3. 媒体**只处理第一个**，优先级 IMAGE>VIDEO>FILE>VOICE
4. `silk-wasm` 在 **devDependencies** + 动态 import —— 生产环境语音大概率拿到 raw `.silk`
5. 主动投递的多账号定位**依赖 contextToken 表**，收件人必须先和 bot 有过会话

## 8. 对 DSH 复刻的含义

| 官方行为 | DSH 侧对应 | 差距 |
|---|---|---|
| 整段投递回复 | `agent.whenIdle()` 后取最终输出 | 无差距，DSH 天然如此 |
| 工具进度通知 | 需监听 `agent/assistant-stream` 或 `session/event` | **需自建**，DSH 无对应抽象 |
| 宿主 cron 投递接口 | 需自建「主动投递」能力 | **DSH 无 channel outbound seam，需自建** |
| 串行阻塞轮询 | DSH 侧可改进（长轮询与处理解耦） | **可优于官方** |
| 无 /stop 打断 | DSH 有 `agent.cancel()` | **可优于官方** |
| 群聊未实现 | 与用户「只单聊」一致 | 需求吻合，无需补 |
| 引用消息影响模型输入 | DSH 的「模型可见⟺logged」要求它必须落 session log | **需设计**，不能像官方那样只放 ctx 字段 |
