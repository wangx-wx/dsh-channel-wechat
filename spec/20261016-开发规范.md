# 开发规范（v1）

> 归档日期：2026-10-16
> 状态：**生效中**
> 来源：用户约定（本轮对话）

## Problem Statement

项目已经推进到 v0.1.1 并发过两次真实事件（Q50 运行时分裂、Q51 诊断不落盘），但仓库里**没有一条成文的
开发流程**：需求从讨论到合入全靠对话记忆，规格散落在 `docs/plan-v1.md` 的 Q 编号里，开发日志堆在仓库根
目录，提交信息是英文散文式描述。新人（或下一次会话的我）无法从仓库本身得知「改动该怎么走」。

## Solution

把开发流程固化成五条规范并写进 `CLAUDE.md`，同时把两个目录结构调整落到实处：
开发日志移入 `docs/dev-log/`，新建 `spec/` 归档规格。约定讨论结果、被推翻的规格、每版本的变更
记录都**留在仓库里**，而不是留在对话里。

## 规范

### 1. 提交代码

完成一个任务、测试通过后**先提交**。格式：

```
type(scope): desc
```

type 取 `feat` / `fix` / `docs` / `style` / `refactor` / `test` / `chore` / `perf`。

**不追溯改写历史提交**：现有提交是符合本仓库风格的英文散文式描述，重写历史的风险大于收益。
新提交按此格式。

### 2. 规约归档

- 目录：`spec/`
- 文件名：**日期递增**，`YYYYMMDD-<slug>.md`
- 格式：参考 `/to-spec` —— Problem Statement / Solution / User Stories / Implementation Decisions /
  Testing Decisions / Out of Scope / Further Notes
- **被推翻的规格打标记**，指向取代它的文件；**不删除**。依据是 `docs/plan-v1.md` 的既有先例：
  Q42 推翻了「提问卡留 v2」、Q47 推翻了「`/cwd` v1 可用」，两处都是原文保留 + 标注修订。

### 3. 开发日志

- 目录：`docs/dev-log/`（原 `开发日志.md` 已移入）
- 提交节奏：**每个版本一次**
- 内容：详细的变更记录，含**被推翻的判断与实测证据**。

  这一条不是形式要求。本仓库已有三次「先写进文档的乐观结论后来被实测推翻」的记录
  （Q47 文档比代码乐观、Q48 安装指令三条全错、Q52 自己推翻了自己的正确方向），
  把它们留在日志里是唯一的防复发手段。

### 4. 开发流程

```
确定需求
  → 从 origin/main 切需求分支（dev_<需求>_<yyMMdd>）
  → 更新或归档规格
  → 用 /tdd 开发与测试（垂直切片：一个测试 → 一个实现 → 重复）
  → 每个小功能完成即提交
  → 推送到远程
  → 整体完成后等用户确认，再合入 main
```

**合入 main 需要用户确认**，不是自动流程。

### 5. 发版

记录开发日志 → `npm publish` → 打 tag → 建 GitHub Release。
具体步骤以 `docs/release.md` 为准（含 2FA、staged publishing 占位版、tag 需要单独推送三个实测点）。

## Implementation Decisions

- 规范同时写进 `CLAUDE.md`（给未来的会话读）与本文件（归档）：`CLAUDE.md` 是入口，`spec/` 是出处。
- `开发日志.md` 用 `git mv` 移到 `docs/dev-log/开发日志.md`，保留历史。
- README 两份（中文 / 英文）的「文档」表同步更新，指向新位置并补上 `spec/`。
- `spec/` 不设 `README.md` 索引：文件名自带日期与主题，排序即索引。条目多了再加。

## Testing Decisions

本规范是流程约定，**没有可测的行为**，不写测试。它的执行情况通过 `git log` 与目录内容可观察。

## Out of Scope

- 迁移 `docs/plan-v1.md` 的决策台账到 `spec/`。
  **不做**：Q1–Q52 是被代码与测试反复引用的一处台账（README 与 `docs/release.md` 都在引用
  `§Q42` / `§Q45` / `§Q50` 这类锚点），拆散会让所有引用失效。新规格进 `spec/`，旧台账留在原地。
- CI 与自动化门禁。
- 追溯改写历史提交信息。

## Further Notes

规范里没有「写单元测试」这类通用建议——本仓库的测试纪律已经沉淀在 `CLAUDE.md` 的
「测试纪律」一节，其中最要紧的一条是：**单测自己注入协作者，因此观察不到 `apply` 有没有把它接上**，
这个缺陷模式已经复发至少四次，所以每处新增生产接线都要补一个真实 `apply` 启动的集成测试。
